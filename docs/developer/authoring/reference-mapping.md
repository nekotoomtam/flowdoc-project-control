# เลือกรูปแบบโครงจากเอกสารต้นแบบ

## Authority Boundary

Project Control เป็นเจ้าของแนวทางถอดแบบนี้ สำหรับชุดปัจจุบันตาม
[baseline](README.md). เป็นคำแนะนำการเลือกใช้ ไม่เพิ่ม schema หรือรับรองว่า
ทุกกรณีผ่าน renderer. งานปรับคู่มือแบบ single-room ตามคำขอผู้ใช้;
execution IDs ไม่เกี่ยวข้อง. ไม่เปลี่ยน runtime, draft หรือสิทธิ์ publish.

## 1. อ่านหน้าที่และรูปลักษณ์ก่อนเลือก node

ดูข้อมูลและภาพจริง ไม่เลือก Format จากชื่อรายงาน/แบบฟอร์ม/หัวข้อเพียงอย่างเดียว.
เก็บก่อนประกอบโครง: ความหมายของหัวข้อ/ช่องกรอก/ตาราง; คู่ข้อมูลและกลุ่ม;
แนว คอลัมน์ อักษร ระยะ เส้น กรอบ ภาพ พื้นที่ว่าง; กฎข้อมูลยาว/เพิ่มลด/ข้ามหน้า.
ช่องว่างหรือเส้นที่ไม่มีข้อความยังเป็นส่วนต้นฉบับ ต้องนับใน coverage ด้วย.
ตารางจัดแนวไม่จำเป็นต้องมีกรอบที่มองเห็น. อย่าเพิ่มกรอบ รวมรายการ ลบเส้น
หรือย่ออักษรเพื่อให้สร้างง่ายหรือจำนวนหน้าตรง; ขนาดจากตัวอย่างไม่ใช่สูตรทุกงาน.

## 2. เลือกหมวดตามลักษณะการจัดหน้า

เนื้อหาไหลใช้ [flowing-book](document-families/flowing-book.md); แบบฟอร์มใช้กรณีด้านล่าง.
เอกสารผสมเลือกเป็นรายส่วน เปิดเฉพาะหัวข้อที่พบ; ไม่อ่านหมวดเล่มไหลแทนทุกกรณี.
ก่อนสร้าง draft จัดสิ่งที่พบใน mapping เดิม ไม่สร้างรายงาน/ขั้นอนุมัติเพิ่ม:

| สถานะ | หลักฐานและสิ่งที่ทำต่อ |
| --- | --- |
| รองรับตรง | สัญญารุ่นปัจจุบันรองรับ; ยังต้อง preview เทียบจริง |
| วิธีทดแทน | บอกส่วนที่แทนและความต่าง; ใช้ได้ตามขอบเขต แต่ยังไม่ใช่ PASS ความเหมือน |
| ข้อจำกัดยืนยันแล้ว | ระบุชั้น plugin/Service/Core และรุ่น พร้อมสัญญาที่ไม่รองรับ หรือกรณีเล็กที่ถูกสัญญาและพิสูจน์ปัญหาได้; เก็บหลักฐาน/ผลกระทบ |
| ต้องลองแก้/ยังไม่ทราบ | ของหาย ค่าผิด ระยะผิด หรือยังไม่ทดสอบ; ระบุการลองถัดไปในงบเดิม ห้ามเรียกข้อจำกัดจากการล้มครั้งเดียว |

**แบบฟอร์มตำแหน่งตายตัว:** วัดจุดเริ่ม/จบเส้น baseline ช่องกรอก แนวข้อความ
และกลุ่มลงนาม แยกข้อมูลว่างจากกราฟิก. ตรวจเฉพาะ [node](nodes.md) และ
[layout](layout.md) ที่ต้องใช้: ฟอนต์ เส้นประ เส้นแต่ละด้าน ความหนา และตำแหน่งที่รองรับ.
การไม่มี property ในรุ่นนี้ไม่พิสูจน์ว่าไม่มีวิธีประกอบอื่น; ของที่ยังไม่ได้ทำยังเป็นงานค้าง.
ฟอนต์ชื่อ/ขนาดใกล้กันอาจกว้างต่างกัน: วัดข้อความสั้นที่เป็นตัวแทนก่อนจัดทั้งหน้า.
ถ้าจำเป็นต้องทดแทน ให้บันทึกฟอนต์ ขนาด ความกว้าง/ความสูงที่วัด และความต่าง;
ไม่มีตัวคูณลดขนาดสากล และห้ามลดเพื่อบังคับจำนวนหน้า. เก็บต้นฉบับไว้.
ภาพให้แยกพิกเซลเดิม กรอบที่ PDF วาด และสัดส่วนที่ถูกยืด; เตรียม asset เมื่อจำเป็น
ตามการแปลงที่พบจริง เก็บภาพเดิมและที่มา ไม่ยกภาพทั้งหน้ามาแทน native text/table.
แก้ input/ระยะที่รับผิดชอบก่อน; validate ผ่านไม่รับรอง render หรือภาพตรง.
หากติดข้อจำกัดจริง ส่งกรณีเล็กและความต่างที่ค้าง ไม่ข้าม gate หรือหยุดส่วนอื่นที่ทำต่อได้.

## 3. ตารางจัดแนวที่มองไม่เห็นกรอบ

รายการคำศัพท์–คำอธิบาย/สัญลักษณ์–ความหมายที่ต้นฉบับไม่มีเส้น ต้องไม่เพิ่มกรอบ.
Area18 table มี `borderColor` แต่ไม่มี border:none/showBorders:false/borderWidth:0;
เส้นยังหนา 0.5pt และสีดำเมื่อละสี. บนพื้นขาวสม่ำเสมอใช้วิธีทดแทนด้านภาพนี้ได้:

```json
{"headerRowCount":0,"repeatHeaderRows":false,"borderColor":"FFFFFF"}
```

นี่เป็น props fragment; ต้องมีกราฟ table/row/cell/content ตาม [Node reference](nodes.md).
headerRowCount:0 เฉพาะเมื่อไม่มีหัวจริง. สีขาวยังเป็น stroke ไม่ใช่โปร่งใส/ปิดเส้น;
พื้นสี/ภาพ/สี cell ต่างกันอาจเห็นรอยต่อ แม้สีตรงพื้นต้อง preview ทุกแถวและหน้าต่อ.
ถ้าต้องไม่มีเส้นจริงให้ระบุช่องว่างความสามารถ ไม่อ้างว่ารองรับแล้ว.
หนึ่งรายการต่อแถว แยก schema คำ/ความหมายหรือภาพ/คำอธิบาย ใช้ array ทำซ้ำ;
อย่ารวมทั้งรายการไว้คนละ cell จนคู่คลาด หรือเพิ่มหัว สี และกรอบที่ต้นฉบับไม่มี.

## 4. การจัดแนวต้องระบุพื้นที่อ้างอิง

คำว่า “กลาง” ต้องระบุว่าเป็นกลางกระดาษ กลาง body กลาง band กลางคอลัมน์
หรือกลางพื้นที่ข้อความใน cell หลังหัก padding. จุดเหล่านี้ไม่จำเป็นต้องตรงกัน.
บันทึกการจัดแนวแต่ละบทบาทจากต้นแบบ: หัวเรื่อง หัวตาราง รหัส คำอธิบาย
ชื่อผู้ลงนาม และเลขหน้า ไม่เหมารวมว่าทุกหัวข้อต้องกลางหรือทุกข้อความต้องซ้าย.

- `textAlign:center` จัดข้อความในพื้นที่ที่ block ได้รับ ไม่เลื่อน block ไปกลางหน้า.
  ใช้ได้ใน cell หรือ band ตามสัญญาปัจจุบัน; root text-block ใน body
  ไม่รับ property นี้. หากต้องจัดกลางใน body ให้พิจารณา table-cell ที่มีกรอบ
  พื้นที่ตามต้องการ พร้อมข้อจำกัดเส้นตารางในบท 3; ไม่ย้ายเนื้อหาไป header เพื่อเลี่ยงข้อจำกัด.
- ไม่กำหนด textAlign จะใช้ left. ชื่อ style เช่น title/heading ไม่ได้ทำให้กลางเอง.
  กำหนดบน text-block ไม่ใช่ table-row/table-cell หรือ TextStyle.
- กลาง cell คิดหลังหัก padding: padding ซ้ายขวาไม่เท่ากันทำให้จุดกลางข้อความ
  ต่างจากกลางกรอบ cell. ตรวจทั้งกรอบและตำแหน่งข้อความที่เรนเดอร์จริง.
- กลาง body/band เท่ากับกลางกระดาษเฉพาะเมื่อขอบซ้ายขวาสมมาตร.
  ตรวจ margin และ band placement แยกกัน ไม่ใช้ image.align แทน textAlign.
- แยกจัดกลางแนวนอนจากแนวตั้ง. `verticalAlign` ไม่ใช่กฎจัดกลางทั่วไป;
  ใช้ได้เฉพาะ fixed cover block ตาม [Node reference](nodes.md).

### เลขหน้า: เนื้อหา ตำแหน่ง และลำดับเป็นคนละเรื่อง

ใช้ system-page-field เพื่อคำนวณเลขหน้า แต่ต้องประกอบตำแหน่งตามต้นแบบด้วย.
ระบุว่าต้องอยู่กลางพื้นที่ใด อยู่เหนือ/ใต้เส้น อยู่แถวเดียวกับ copyright/version
หรือแยกแถว และห่างจากขอบล่าง/เนื้อหาเท่าไร. การอยู่ใน footer ถูกต้องยังไม่พอ.

band.fragment.rootIds เรียงแนวตั้งตามลำดับ; children ในแต่ละ column ก็เช่นกัน.
ตัวอย่างลำดับต่อไปนี้เป็นแนวประกอบ ไม่ใช่ definition เต็ม:

```text
เลขหน้าเหนือเส้น:  [page-label, separator, metadata-columns]
เลขหน้าใต้เส้น:    [separator, page-label, metadata-columns]
เลขหน้าแถวเดียวกับ metadata: [separator, metadata-and-page-columns]
```

ชื่อเหล่านี้ต้องอ้าง node ที่ประกาศจริง. แบบแยกแถวใช้ page-label เป็น text-block
เต็มความกว้าง band และจัดกลาง; หาก band ไม่สมมาตรยังต้องแก้พื้นที่อ้างอิงก่อน.
แบบแถวเดียวกันใช้ columns แต่ห้ามถือว่า column ที่สองอยู่กลางหน้าเสมอ.

ตัวอย่าง band กว้าง W, สามคอลัมน์ weight 4:2:2 และ gap g เท่ากัน:
ความกว้างที่แบ่งได้ R=W−2g; จุดกลางคอลัมน์ที่สองอยู่ที่ 5R/8+g
จึงเยื้องจากกลาง band เป็น W/8−g/4. แม้ textAlign:center ก็ยังเยื้อง.
ถ้าต้องอยู่กลาง band ให้จัดพื้นที่ด้านซ้าย/ขวาสมมาตร เช่น weight 1:1:1
หรือแยกเลขหน้าเป็นอีกแถวเต็ม band โดยเลือกตามต้นแบบ ไม่ใช้สูตรเดียวทุกงาน.
ชื่อ node ว่า center ไม่ใช่คำสั่งจัดตำแหน่ง.

ข้อความเลขหน้าที่จัดกลาง/ขวาใน band และมี system-page-field ต้องใช้
`pageFieldLayout:"compact"` ตามสัญญา. ดู [ตัวอย่าง footer](layout.md).
เมื่อลำดับ/ความสูง band เปลี่ยน ให้ตรวจระยะจาก body และขอบกระดาษอีกครั้ง.
ทดสอบเลขหลักเดียวและหลายหลักตามขนาดเอกสาร ตรวจการตัดบรรทัดของ metadata
และหน้าต่อเนื่องในทุก Section ที่มี footer. ตรวจเลขหน้าที่แสดงแยกจาก index PDF
เมื่อมี cover excluded หรือ numbering restart.

## 5. เมื่อ PDF และข้อมูลที่รับมาไม่ตรงกัน

แยกแหล่งหลักของ **ข้อมูล** และ **รูปแบบ** ตามผู้ใช้; อย่าคัด PDF เก่าทับ JSON ใหม่
ที่ผู้ใช้ให้ยึด. ถ้ายังไม่รู้แหล่งหลักและกระทบเนื้อหา เก็บทั้งสองพร้อมตำแหน่ง
แล้วถามเฉพาะจุด โดยทำส่วนอื่นต่อ. อย่าลบคำนำหน้า ชื่อในวงเล็บ หน่วย หมายเหตุ
ไอคอน หรือช่องกรอก; “กระชับกว่า” ไม่ใช่อนุมัติ. แยกความต่างที่ผู้ใช้ตั้งใจไว้
จากสิ่งที่รอตัดสินใจ และใช้สถานะในข้อ 2 สำหรับความสามารถ/งานแก้ที่ยังเหลือ.

## 6. ตรวจสามด้านก่อนส่ง review

1. **ข้อมูล:** เทียบรายการจากต้นทางกับ PDF จริงหลังแยก cell ตรวจจำนวน ลำดับ
   คู่ข้อมูล และรายการซ้ำ. ค้นทั้งก้อน/นับรหัสไม่พอ; ค่าที่ไม่พบต้องแยกปัญหา
   ดึงข้อความ/แยกช่องจากข้อมูลหาย แล้วสรุปหรือระบุ unresolved ทุกค่า.
2. **พฤติกรรม:** validate/compose/render, สารบัญและลิงก์, ข้อมูลเพิ่มลด/ยาว/ว่าง
   ตามส่วนที่เปลี่ยน. ตรวจเลขหน้าที่พิมพ์กับปลายทางจริง ไม่อนุมานจากลิงก์อย่างเดียว.
3. **ภาพและการใช้งาน:** เทียบทุกหน้าตามส่วนเนื้อหา แม้เลขหน้าไม่ตรง ตรวจอักษร
   ระยะ เส้น กรอบ ภาพ สี คอลัมน์ ช่องลงชื่อและหน้าต่อ. หน้าลดไม่ยืนยันว่าดีขึ้น/ครบ.

รายงานแยกผลสามด้าน พร้อมความต่างที่ยังเหลือและขอบเขตการตรวจจริง.
ไม่เปลี่ยนผลรอบก่อนย้อนหลัง และไม่ใช้ผลจาก request ที่สร้างเองยืนยันว่าถอดต้นทางครบ.
เมื่อ PDF พร้อม review ให้คง draft; publish ยังต้องรอผู้ใช้ยืนยัน.
