# เลือกรูปแบบโครงจากเอกสารต้นแบบ

## Authority Boundary

Project Control เป็นเจ้าของแนวทางถอดแบบนี้ สำหรับ candidate ตาม
[baseline](README.md). เป็นคำแนะนำการเลือกใช้ ไม่เพิ่ม schema หรือรับรองว่า
ทุกกรณีผ่าน renderer. งานปรับคู่มือแบบ single-room ตามคำขอผู้ใช้;
execution IDs ไม่เกี่ยวข้อง. ไม่เปลี่ยน runtime, draft หรือสิทธิ์ publish.

## 1. อ่านหน้าที่และรูปลักษณ์ก่อนเลือก node

ใช้หลักเดียวกันกับรายงาน แบบฟอร์ม คู่มือ และเอกสารข้อกำหนด ไม่เลือก Format
จากชื่อหัวข้อเพียงอย่างเดียว. คำว่า Element, Legend, Definitions หรือคำศัพท์
อาจมีโครงต่างกันในแต่ละเอกสาร ให้ดูรายการจริงและภาพต้นแบบก่อน.

แยกสิ่งที่ต้องบันทึกก่อนประกอบโครง:

- **ความหมาย:** หัวข้อ คำอธิบาย รายการคู่ ช่องกรอก ช่องลงชื่อ หรือข้อมูลตาราง.
- **ความสัมพันธ์:** อะไรอยู่แถวเดียวกัน อะไรเป็นคนละรายการ และอะไรอยู่กลุ่มเดียวกัน.
- **รูปลักษณ์:** แนวซ้ายขวา สัดส่วนคอลัมน์ ขนาดอักษร ระยะบรรทัด padding
  พื้นหลัง เส้น ภาพ และพื้นที่ว่างที่ใช้ทำงานจริง.
- **กฎเมื่อข้อมูลเปลี่ยน:** เพิ่มรายการ ข้อความยาว ข้ามหน้า และหัวข้อเริ่มหน้าใหม่.

การจัดแนวด้วยตารางไม่บังคับว่าผู้อ่านต้องเห็นกรอบตาราง.
อย่าเพิ่มกรอบ รวมรายการ ลบเส้น หรือย่ออักษรเพื่อให้สร้างง่ายหรือได้จำนวนหน้าเป้าหมาย.
ตัวเลข 98 หน้า ชื่อบท และขนาดอักษรจากตัวอย่างหนึ่งไม่ใช่กติกาของทุกเอกสาร.

## 2. เลือกหมวดตามลักษณะการจัดหน้า

ปัจจุบันมี [เอกสารแบบเล่มที่เนื้อหาไหลต่อข้ามหน้า](document-families/flowing-book.md)
ซึ่งรวมกรณีที่พบ วิธีเลือก และตัวอย่างรายการสำรวจก่อนประกอบโครง.
อ่านหลักร่วมในบทนี้ แล้วเปิดเฉพาะหมวด/กรณีที่เกี่ยวข้อง ไม่ต้องโหลดทุก reference.

ชื่อ SRS รายงาน หรือสัญญาเป็นประเภทการใช้งาน ไม่ใช่กฎ layout โดยอัตโนมัติ.
เมื่อมีงานลักษณะอื่นจริงจึงเพิ่มหมวด; ไม่สร้างหมวดว่างหรือคัดหลักร่วมซ้ำ.
เอกสารผสมให้เลือกวิธีเป็นรายส่วนและบันทึกข้อยกเว้น.

## 3. ตารางจัดแนวที่มองไม่เห็นกรอบ

ตัวอย่างทั่วไปคือรายการคำศัพท์–คำอธิบาย และรายการสัญลักษณ์–ความหมาย.
หัวข้อชื่อ Element หรือ KEY DEFINITIONS เป็นเพียงตัวอย่างชื่อ ไม่ใช่ตัวกระตุ้น
ให้ใช้รูปแบบเดียวกันทุกครั้ง. ถ้าต้นฉบับไม่มีเส้น ให้ตั้งเป้าผลภาพไม่มีเส้นเช่นกัน.

สำหรับ candidate Area18 ปัจจุบัน table มี `borderColor` แต่ไม่มีสวิตช์
ปิดเส้น ไม่มี `border:none`, `showBorders:false` หรือ borderWidth:0.
renderer ยังสร้างเส้นความหนา 0.5pt; การละ borderColor ให้ผลเส้นสีดำ.
บนพื้นขาวสม่ำเสมอสามารถใช้ fragment ของ table.props นี้เป็นวิธีทดแทนด้านภาพ:

```json
{"headerRowCount":0,"repeatHeaderRows":false,"borderColor":"FFFFFF"}
```

นี่ไม่ใช่ table node เต็ม ต้องประกอบ id/type/columns/rowIds และ cell/content
ตาม [Node reference](nodes.md). ไม่มีแถวหัวจริงจึงใช้ headerRowCount:0;
ถ้ามีแถวหัวจริงให้กำหนดตามต้นแบบ ไม่คัดค่านี้โดยไม่ตรวจ.

เส้นสีขาวยังเป็นเส้นที่วาด ไม่ใช่ความโปร่งใสหรือการปิด stroke.
อย่าใช้เป็นสูตรทั่วไปเมื่อมีพื้นสี ภาพพื้นหลัง หรือ cell สีต่างกัน เพราะอาจเห็นรอยต่อ.
แม้พื้นสีเดียวจะเลือกสีเส้นให้ตรงพื้นได้ ก็ต้อง preview ตรวจขอบทุกแถวและหน้าต่อเนื่อง.
ถ้าต้องการไม่มีเส้นจริง ให้บันทึกเป็นช่องว่างความสามารถ ไม่อ้างว่ารุ่นนี้รองรับแล้ว.

รักษาหนึ่งรายการต่อแถว ไม่เอาคำศัพท์ทั้งหมดไปรวมใน cell ซ้ายและความหมายทั้งหมด
ใน cell ขวา เพราะข้อความยาวทำให้คู่ข้อมูลคลาดกัน. ใช้ schema แยกคำ/ความหมาย
หรือภาพ/คำอธิบาย และทำซ้ำจาก array เมื่อจำนวนรายการเปลี่ยนได้.
ไม่สร้างหัวตาราง สีพื้น หรือกรอบรอบกลุ่มที่ไม่มีในต้นแบบ.

## 4. การจัดแนวต้องระบุพื้นที่อ้างอิง

คำว่า “กลาง” ต้องระบุว่าเป็นกลางกระดาษ กลาง body กลาง band กลางคอลัมน์
หรือกลางพื้นที่ข้อความใน cell หลังหัก padding. จุดเหล่านี้ไม่จำเป็นต้องตรงกัน.
บันทึกการจัดแนวแต่ละบทบาทจากต้นแบบ: หัวเรื่อง หัวตาราง รหัส คำอธิบาย
ชื่อผู้ลงนาม และเลขหน้า ไม่เหมารวมว่าทุกหัวข้อต้องกลางหรือทุกข้อความต้องซ้าย.

- `textAlign:center` จัดข้อความในพื้นที่ที่ block ได้รับ ไม่เลื่อน block ไปกลางหน้า.
  ใช้ได้ใน cell หรือ band ตาม candidate ปัจจุบัน; root text-block ใน body
  ไม่รับ property นี้. หากต้องจัดกลางใน body ให้พิจารณา table-cell ที่มีกรอบ
  พื้นที่ตามต้องการ พร้อมข้อจำกัดเส้นตารางในบท 3; ไม่ย้ายเนื้อหาไป header เพื่อเลี่ยงข้อจำกัด.
- ไม่กำหนด textAlign จะใช้ left. ชื่อ style เช่น title/heading ไม่ได้ทำให้กลางเอง.
  กำหนดบน text-block ไม่ใช่ table-row/table-cell หรือ TextStyle.
- กลาง cell คิดหลังหัก padding: padding ซ้ายขวาไม่เท่ากันทำให้จุดกลางข้อความ
  ต่างจากกลางกรอบ cell. ตรวจทั้งกรอบและตำแหน่งข้อความที่เรนเดอร์จริง.
- กลาง body/band เท่ากับกลางกระดาษเฉพาะเมื่อขอบซ้ายขวาสมมาตร.
  ตรวจ margin และ band placement แยกกัน ไม่ใช้ image.align แทน textAlign.
- แยกจัดกลางแนวนอนจากแนวตั้ง. `verticalAlign` ไม่ใช่กฎจัดกลางทั่วไป;
  ใช้ได้เฉพาะ fixed cover block ตาม [Node reference](nodes.md).

### เลขหน้า: เนื้อหา ตำแหน่ง และลำดับเป็นคนละเรื่อง

ใช้ system-page-field เพื่อคำนวณเลขหน้า แต่ต้องประกอบตำแหน่งตามต้นแบบด้วย.
ระบุว่าต้องอยู่กลางพื้นที่ใด อยู่เหนือ/ใต้เส้น อยู่แถวเดียวกับ copyright/version
หรือแยกแถว และห่างจากขอบล่าง/เนื้อหาเท่าไร. การอยู่ใน footer ถูกต้องยังไม่พอ.

band.fragment.rootIds เรียงแนวตั้งตามลำดับ; children ในแต่ละ column ก็เช่นกัน.
ตัวอย่างลำดับต่อไปนี้เป็นแนวประกอบ ไม่ใช่ definition เต็ม:

```text
เลขหน้าเหนือเส้น:  [page-label, separator, metadata-columns]
เลขหน้าใต้เส้น:    [separator, page-label, metadata-columns]
เลขหน้าแถวเดียวกับ metadata: [separator, metadata-and-page-columns]
```

ชื่อเหล่านี้ต้องอ้าง node ที่ประกาศจริง. แบบแยกแถวใช้ page-label เป็น text-block
เต็มความกว้าง band และจัดกลาง; หาก band ไม่สมมาตรยังต้องแก้พื้นที่อ้างอิงก่อน.
แบบแถวเดียวกันใช้ columns แต่ห้ามถือว่า column ที่สองอยู่กลางหน้าเสมอ.

ตัวอย่าง band กว้าง W, สามคอลัมน์ weight 4:2:2 และ gap g เท่ากัน:
ความกว้างที่แบ่งได้ R=W−2g; จุดกลางคอลัมน์ที่สองอยู่ที่ 5R/8+g
จึงเยื้องจากกลาง band เป็น W/8−g/4. แม้ textAlign:center ก็ยังเยื้อง.
ถ้าต้องอยู่กลาง band ให้จัดพื้นที่ด้านซ้าย/ขวาสมมาตร เช่น weight 1:1:1
หรือแยกเลขหน้าเป็นอีกแถวเต็ม band โดยเลือกตามต้นแบบ ไม่ใช้สูตรเดียวทุกงาน.
ชื่อ node ว่า center ไม่ใช่คำสั่งจัดตำแหน่ง.

ข้อความเลขหน้าที่จัดกลาง/ขวาใน band และมี system-page-field ต้องใช้
`pageFieldLayout:"compact"` ตามสัญญา. ดู [ตัวอย่าง footer](layout.md).
เมื่อลำดับ/ความสูง band เปลี่ยน ให้ตรวจระยะจาก body และขอบกระดาษอีกครั้ง.
ทดสอบเลขหลักเดียวและหลายหลักตามขนาดเอกสาร ตรวจการตัดบรรทัดของ metadata
และหน้าต่อเนื่องในทุก Section ที่มี footer. ตรวจเลขหน้าที่แสดงแยกจาก index PDF
เมื่อมี cover excluded หรือ numbering restart.

## 5. เมื่อ PDF และข้อมูลที่รับมาไม่ตรงกัน

แยกแหล่งอ้างอิง **ข้อมูล** และ **รูปแบบ** ตามคำสั่งผู้ใช้ก่อน.
ถ้า JSON เป็นข้อมูลใหม่ที่ผู้ใช้ระบุให้ยึด การต่างจาก PDF เก่าอาจตั้งใจไว้;
อย่าคัดค่าเก่าทับข้อมูลใหม่เพียงเพื่อให้ภาพเหมือน.
หากยังไม่ได้กำหนดแหล่งหลักและความต่างมีผลต่อเนื้อหา ให้จดค่าทั้งสองพร้อมตำแหน่ง
แล้วถามเฉพาะจุดนั้น โดยทำส่วนที่ไม่ขึ้นกับคำตอบต่อได้.

อย่าลบคำนำหน้า ชื่อเล่นในวงเล็บ หน่วย หมายเหตุ ไอคอน หรือช่องกรอกเงียบ ๆ.
จัดรายการความต่างเป็น: ผู้ใช้กำหนดไว้ / ยังต้องตัดสินใจ / ข้อจำกัดระบบ /
ความผิดพลาดที่ต้องแก้. การอธิบายว่า “กระชับกว่า” ไม่ใช่การอนุมัติเปลี่ยนรูปแบบ.

## 6. ตรวจสามด้านก่อนส่ง review

1. **ข้อมูล:** ทำรายการจากต้นทาง แล้วตรวจย้อนกลับใน PDF ที่สร้างจริง.
   เทียบค่าหรือรายการตามความหมายหลังแยก cell ไม่ใช้เพียงการค้นทั้งก้อน.
   ตรวจจำนวน ลำดับ คู่ข้อมูล และรายการซ้ำ; จำนวนรหัสเท่ากันยังไม่ยืนยันข้อความครบ.
   ถ้าการค้นไม่พบ ให้แยกว่าเป็นการแยกช่อง/การดึงข้อความ หรือข้อมูลหายจริง.
   ทุกค่าที่ไม่พบต้องมีข้อสรุปหรือระบุ unresolved; ห้ามประกาศครบโดยมองข้ามรายการนี้.
2. **พฤติกรรม:** validate/compose/render, สารบัญและลิงก์, ข้อมูลเพิ่มลด/ยาว/ว่าง
   ตามส่วนที่เปลี่ยน. ตรวจเลขหน้าที่พิมพ์กับปลายทางจริง ไม่อนุมานจากลิงก์อย่างเดียว.
3. **ภาพและการใช้งาน:** เทียบทุกหน้าของงานส่งมอบกับต้นแบบตามส่วนเนื้อหา
   แม้เลขหน้าไม่ตรงกัน. ตรวจอักษร ระยะห่าง เส้น กรอบ ภาพ สี คอลัมน์ ช่องลงชื่อ
   และการต่อหน้า. จำนวนหน้าลดลงไม่ใช่หลักฐานว่า layout ดีขึ้นหรือเนื้อหาครบ.

รายงานแยกผลสามด้าน พร้อมความต่างที่ยังเหลือและขอบเขตการตรวจจริง.
ไม่เปลี่ยนผลรอบก่อนย้อนหลัง และไม่ใช้ผลจาก request ที่สร้างเองยืนยันว่าถอดต้นทางครบ.
เมื่อ PDF พร้อม review ให้คง draft; publish ยังต้องรอผู้ใช้ยืนยัน.
