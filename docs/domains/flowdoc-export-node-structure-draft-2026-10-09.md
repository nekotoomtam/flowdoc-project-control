## เป้าหมายของร่าง

ออกแบบโครงเอกสารที่ใช้สร้าง PDF ต่อจากรุ่น 0.1.5 และเปิดทางให้หน้าบ้าน
อ้างถึงและแก้เนื้อหาเดียวกันได้ในอนาคต เริ่มจากหน้าที่ของ node แล้วค่อยตกลง
การอยู่ภายในกัน ขนาด การไหล ตัวแปร และความเข้ากันได้ แบ่งคุยเป็นพาร์ตย่อย
ได้ตามความจำเป็น โดยยังไม่กำหนดรุ่นส่งมอบหรือลำดับลงมือทำเป็น roadmap

โจทย์ที่ต้องเผื่อคือเอกสาร UAT หรือเอกสารเล่มยาวที่ผู้สร้างกำหนดรูปแบบไว้
แต่ผู้ใช้ส่งข้อมูลและลำดับโครงย่อยได้ ภายในเซลล์อาจต้องมีข้อความหลายส่วน
และรูปภาพร่วมกัน รูปแบบนี้เป็นเป้าหมายที่จะออกแบบ ไม่ใช่ความสามารถที่รองรับแล้ว

## หลักที่ตกลงใช้เป็นทิศทาง

1. ออกแบบเผื่อหน้าบ้าน แต่ยังไม่สร้างหน้าบ้านในรอบออกแบบนี้
2. แยกโครงเอกสาร ผลคำนวณจัดหน้า และสถานะการแก้ไขบนหน้าบ้านออกจากกัน
3. การแก้เนื้อหาของ node เดิมควรรักษา identity ของมันไว้ การคัดลอกหรือทำซ้ำ
   เป็นอีก instance ต้องมี identity แยก โดยความสัมพันธ์กับต้นแบบต้องอธิบายได้
4. การข้ามหน้าไม่ควรสร้าง authored node ใหม่เพียงเพราะพื้นที่กระดาษหมด
   ส่วนที่แสดงแต่ละหน้าต้องอ้างกลับ node และช่วงเนื้อหาต้นทางได้
5. แยกค่าที่ผู้สร้างกำหนดจากค่าที่ layout คำนวณ เช่น ความสูงตามเนื้อหา
   ไม่เขียนทับเป็นความสูงตายตัวของต้นฉบับ
6. ทุกพาร์ตต้องตอบว่า “ถ้ามีหน้าบ้านมาแก้สิ่งนี้ จะอ้างถึงและเปลี่ยนมันอย่างไร”
   การแก้เฉพาะส่วนเป็นเป้าหมายออกแบบ ยังไม่ใช่คำรับรอง incremental layout
   หรือความลื่นขณะพิมพ์ และยังไม่เลือก revision/cache protocol

### ทิศทาง Adapter ที่ตกลงเพิ่มเติม

ระยะนี้เน้นโครงหลังบ้านสำหรับ export ก่อน หน้าบ้านในอนาคตสามารถแปลงโครงนี้
เป็นรูปข้อมูลที่เหมาะกับการแก้ไข แล้วใช้ Adapter แปลงกลับตอนบันทึกหรือออกไฟล์
ต้องรักษา identity ลำดับ ความสัมพันธ์ ตัวแปร หน่วย และความหมายครบ
การแปลงไป–กลับโดยไม่แก้ต้องได้เอกสารเทียบเท่าเดิม ไม่จำเป็นต้องเรียง JSON เหมือนเดิม
สถานะ selection/เคอร์เซอร์/zoom แยกจากความหมายเอกสาร
พรีวิวที่ต้องตรงกับ PDF ให้ใช้ Core วัดข้อความ/wrap/layout ภายใต้ข้อมูล ฟอนต์
และกติกาเดียวกัน; Adapter ไม่สร้างกติกาตัดบรรทัดหรือแบ่งหน้าอีกชุด
ยังไม่สร้าง Adapter หรือสัญญาผลจัดหน้าสาธารณะสำหรับ frontend ใน slice แรก

## คำที่ต้องใช้ให้ตรงกัน

อ้างอิง [Product terminology](flowdoc-product-terminology.md) โดยร่างนี้กำหนดขอบเขตดังนี้:

- `Core runtime node` — define: องค์ประกอบในโครงเอกสารของ Core ไม่ใช่ Node ของ Project Control
- โครงเอกสาร — split: แม่แบบที่ยังมีตัวแปร กับเอกสารที่ผูกข้อมูลแล้ว ต้องระบุว่าพูดถึงฝั่งไหน
- หน้าบ้าน — split: เครื่องมือสร้างแม่แบบ กับหน้ากรอกข้อมูลในแม่แบบ เป็นคนละขอบเขตสิทธิ์และคำสั่ง ยังไม่เลือกทำอย่างใดในรอบนี้
- กล่อง — context-only: ต้องระบุว่าเป็นกรอบเนื้อหา กรอบเซลล์ หรือกรอบ selection ก่อนแปลงเป็นกติกา
- container — context-only: เป็นชื่อแนวคิดสำหรับจัดกลุ่ม ยังไม่ยืนยันว่าจะเพิ่มชนิด node นี้
- เวอร์ชัน — split: รุ่นซอฟต์แวร์ รุ่นโมเดล และเวอร์ชันแม่แบบ ไม่ใช้แทนกัน

## พาร์ตที่จะคุย

ตารางนี้เป็นหัวข้อออกแบบ ไม่ใช่ขั้นลงมือพัฒนาหรือข้อผูกมัดว่าต้องสร้างทุกอย่าง

| พาร์ต | เรื่องที่ต้องตกลง | สิ่งที่ควรได้เมื่อคุยจบ |
| --- | --- | --- |
| 1 หน้าที่ของ node | อะไรเป็นเนื้อหา อะไรจัดกลุ่ม อะไรจัดวาง อะไรเป็นผลที่ระบบสร้าง | รายการชนิดที่จำเป็น พร้อมหน้าที่และตัวอย่าง |
| 2 แม่และลูก | ชนิดลูกที่รับได้ จำนวน/ความลึก ลำดับ และความหมายของเพิ่ม ย้าย คัดลอก ลบ | ตารางความสัมพันธ์และกติกา identity |
| 3 ขนาดและพื้นที่ | ความกว้าง/สูง ค่าคงที่/ตามเนื้อหา padding และระยะระหว่างลูก | กติกาคำนวณที่แยกค่าต้นฉบับจากผลจริง |
| 4 การไหลและข้ามหน้า | จุดแบ่ง สิ่งที่ต้องอยู่ด้วยกัน กรอบต่อเนื่อง หัวซ้ำ และกรณีวางไม่ลง | ตัวอย่างก่อน/หลังแบ่งหน้าและผลล้มเหลวที่ชัดเจน |
| 5 ตัวแปรและการทำซ้ำ | scope, array ที่มีตัวแปรลูก, area สำหรับรายการโครงย่อย, ตัวตนของ instance และการอ้างกลับ | ตัวอย่างนิยาม ข้อมูลเข้า โครงหลังประกอบ และ feedback เมื่อข้ามรายการ |
| 6 ใช้กับของเดิม | รูปแบบเดิมอ่านอย่างไร อะไรเปลี่ยน รุ่นโมเดล การตรึงเวอร์ชัน และการย้ายถ้าจำเป็น | ขอบเขต compatibility รวมผลจาก array/area และตัวอย่างตรวจรับ |

แต่ละพาร์ตแบ่งย่อยได้ บันทึกในเอกสารนี้ก่อน พร้อมแยก “ตกลงแล้ว”
“ข้อเสนอ” และ “ยังเปิดอยู่” ไม่ต้องสร้างเอกสารใหม่ทุกครั้งที่คุย

## พาร์ต 1 ขอบเขตเริ่มต้นที่ตกลงแล้ว

เจ้าของยืนยันให้ค่อยเป็นค่อยไป: ออกแบบให้หนึ่ง cell มี TextBlock และ Image
หลายชิ้นเรียงจากบนลงล่างเป็นลูกโดยตรงก่อน แต่ละชิ้นเป็น node ของตัวเอง
ตัวอย่างคือ “ข้อความอธิบาย → รูปหลักฐาน → คำบรรยาย” โดยคำบรรยายใช้ TextBlock
ข้อนี้เป็นขอบเขตการออกแบบที่ยอมรับแล้ว ยังไม่ใช่การรองรับภาพในเซลล์ของรุ่นปัจจุบัน
หรือการอนุมัติ schema และ implementation ทั้งชุด

ยืนยันเพิ่มเติม: cell ชุดแรกไม่รับ Columns ตารางซ้อน หรือกลุ่มซ้อน
ยังรักษาการรวมเซลล์เดิม ชนิดลูกและจำนวนช่องกำหนดในแม่แบบก่อน
ไม่เพิ่มภาพระดับ item ใน array หรือการขยายโครงย่อยผ่าน area ในชุดนี้
Columns ที่เคยทดลองในระบบหน้ากระดาษเก่าไม่ใช่หลักฐานว่ามี Columns node
ใน Core export 0.1.5; `Table.columns` เป็นนิยามคอลัมน์ตารางคนละเรื่องกัน

รอบแรกไม่เพิ่ม node กลุ่มหรือฟิลด์สำรองสำหรับสิ่งที่ยังไม่มีการใช้งานจริง
ไม่ตั้งสมมติฐานว่า cell มีได้เพียง TextBlock เดียวหรือลูกทุกตัวต้องเป็นข้อความ
การเพิ่มชนิดลูกภายหลังยังอาจต้องขยายสัญญาข้อมูลและตรวจความเข้ากันได้

### กรณีอนาคตที่เลื่อนไว้

หนึ่ง cell อาจมีโครงย่อยหลายชุด เช่น “หลักฐาน A” และ “หลักฐาน B”
โดยแต่ละชุดมีข้อความ รูป และตัวแปรของตัวเอง เจ้าของยืนยันว่ามีกรณีใช้งานจริง
แต่เลื่อนการเรียกโครงย่อยภายใน cell ตัวแปรเฉพาะชุด การทำซ้ำชุด และการจัดการ
ทั้งกลุ่มไว้ก่อน รวมถึงยังไม่เพิ่ม container ซ้อนทั่วไป
การเลื่อนนี้ไม่ยกเลิกความสามารถโครงย่อยหรือข้อมูลซ้ำที่มีอยู่ในฐานเดิม

แยกความหมายไว้ว่าโครงย่อยเป็นแบบที่นำมาใช้ ส่วนกลุ่ม node เป็นผลหลังประกอบ
เมื่อกลับมาทำกรณีนี้จึงค่อยตัดสินว่าจะรักษาขอบเขตกลุ่มไว้หรือขยายลูกมาต่อกัน
ยังไม่กำหนด identity ของกลุ่ม กติกาการย้ายทั้งชุด หรือการรักษาชุดเมื่อข้ามหน้า

### ประเด็นที่คุยต่อ

ยังต้องตกลงหน้าที่ของ node ที่เกี่ยวข้องและรายละเอียดแม่–ลูก ขนาด ระยะห่าง
และการแบ่งหน้า โดยใช้ตัวอย่างลูกหลายชิ้นข้างต้นเป็นโจทย์หลัก
ไม่ถือว่าพาร์ต 1 ทั้งหมดเสร็จเพียงเพราะเลือกขอบเขตเริ่มต้นนี้

## พาร์ต 5 — ข้อตกลงที่เก็บไว้ทำภายหลัง

เจ้าของให้เก็บบทสนทนาเรื่องรายการภาพ/โครงย่อยไว้ในพาร์ต 5 และตรวจผลต่อ
ความเข้ากันได้ในพาร์ต 6 ไม่ย้ายมาทำก่อนหรือเป็น prerequisite ของ cell slice

image ยังเป็นภาพเดียว ใช้ array ที่มีตัวแปรลูก image และ caption แทน multiple image
ไม่ทำ array ซ้อน array หรือ area ในช่วงนี้

**สิ่งที่ตรวจพบในโค้ดปัจจุบัน:**

- `src/template/types.ts` และ `validateSchemas.ts`: array items รับ string/link;
  image source รับเฉพาะ global/local; repeats ระบุ tableId/rowTemplateId เท่านั้น
- `src/binding/expandRows.ts`: ทำซ้ำแถวและ clone ลูกตาม itemIndex ได้แล้ว
  แต่ image ยังอ่าน global/local และไม่มีจุดทำซ้ำเฉพาะ cell children
- `src/data/validateValues.ts`: มี required/default, array item path และ image UUID
  validation แล้ว; `prepareGeneration.ts` คืน failure เมื่อข้อมูลที่ตรวจมี error
  จึงใช้กฎนี้ต่อ ไม่ข้าม array item ที่ผิดแบบ area
- Service `src/templates/assembly.ts`: บันทึกตัวแปรลูกผ่าน parentId ได้แล้ว แต่
  checkRecord จำกัดลูก array เป็น type 110001/110005 ต้องเพิ่ม 110004 แบบมี model gate
  master image และ FK มีอยู่แล้ว ไม่พบเหตุให้เพิ่มตารางหรือ master ใหม่จากงานนี้
- Service admission compose ก่อน claim images และ `src/images/job.ts` อ่าน image
  nodes ทั้ง graph หลัง compose; น่าจะใช้ทางเดิมได้ ต้องพิสูจน์ผ่าน real-DB/API

**ทางเลือกการวางจุดทำซ้ำ:** ทำซ้ำทั้ง cell ง่ายแต่หัวข้อคงที่จะถูกทำซ้ำด้วย;
เพิ่ม repeat/container node จะกระทบ graph/layout มากกว่าความต้องการชุดแรก;
ข้อเสนอที่เลือกใช้ร่างนี้คือประกาศชุดลูกต่อเนื่องแยกใน Format แล้วขยายเป็นลูกปกติ
ก่อน layout จึงใช้ paginator 0.1.6 ต่อได้โดยไม่เพิ่ม runtime container

#### สัญญาแม่แบบที่เสนอ

เพิ่ม optional `Format.cellRepeats` ใน node model 10; รุ่น 4–9 ใช้สัญญาเดิม
`Format.repeats` สำหรับแถวคงรูปเดิม ไม่เปลี่ยนเป็น union ที่ทำให้ของเดิมต้องย้าย
ตัวอย่างเฉพาะส่วนของแม่แบบ (ชื่อ field ใหม่เป็นข้อเสนอ):

```json
{
  "cellRepeats": [{
    "id": "repeat-001",
    "cellId": "node-010",
    "childTemplateIds": ["node-012", "node-013"],
    "source": {"scope": "local", "key": "evidenceList"}
  }]
}
```

cell `node-010` เดิมมี childIds `[node-011, node-012, node-013, node-014]`:
หัวข้อคงที่ → รูปต้นแบบ → คำบรรยายต้นแบบ → หมายเหตุคงที่
การประกอบแทนที่ช่วง node-012/013 ด้วยชุดต่อรายการ; ไม่วาดต้นแบบเพิ่มอีกหนึ่งชุด
ใน Image source ใช้ `{scope:"item", key:"photo"}` และ caption ใช้ field-ref
`{scope:"item", key:"caption"}`; global/local ยังต้องระบุชัด ไม่ fallback ข้าม scope

- เริ่มหนึ่ง cellRepeat ต่อ cell; หลาย cell มี declaration ของตนเองได้
- childTemplateIds ต้องไม่ว่าง เป็นลูกโดยตรงที่ติดกันตามลำดับ childIds และเป็น
  TextBlock/Image เท่านั้น; ID หาย ซ้ำ ผิดแม่ หรือลำดับผิดทำให้แม่แบบไม่ผ่าน
- source ต้องชี้ array ใน global/local; items ต้องประกาศลูกอย่างน้อยหนึ่งตัว
  รุ่น 10 รับ string/link/image ต่อ item ไม่รับ array/object field ซ้อน
- ไม่อนุญาต cellRepeat อยู่ใต้ row repeat หรือในหัวตารางใน slice นี้;
  ไม่ปิด row repeats เดิมในบริเวณอื่น และไม่สร้าง item scope ซ้อนโดยปริยาย
- image item bindings ใช้ได้เฉพาะขอบเขต repeat ที่ตรวจ schema ได้จริง;
  เมื่อขยายการรับ image items ใน model 10 ต้องตรวจ row-repeat เดิมด้วย
- พิกัด/ขนาด/padding มาจากแม่แบบเดิม ไม่มากับข้อมูลรายการ
- Core serialized template เดิมอ้างตัวแปรด้วย scope/key ส่วน Service เก็บ variable
  IDs/parent IDs แยกอยู่แล้ว ร่างนี้ไม่เปลี่ยน binding ทั้งระบบเป็น variableId;
  references ของชุด node ใช้ ID จริงเสมอ และ key อ่านตามเวอร์ชันแม่แบบที่ล็อกไว้

#### สิ่งที่ผู้เรียก API ส่ง

ตัวอย่าง envelope ตามทิศ API เดิม โดย UUID ด้านล่างสมมติว่าอยู่ใน upload ที่ finalize
แล้วและของเวอร์ชันนี้มี format `evidence`; ไม่ใช่ fixture ที่เรียกได้ทันที:

```json
{
  "docKey": "uat-report",
  "version": 1,
  "uploadId": "11111111-1111-4111-8111-111111111111",
  "data": {},
  "content": [{
    "format": "evidence",
    "data": {
      "evidenceList": [
        {"photo": "22222222-2222-4222-8222-222222222222", "caption": "ก่อนทดสอบ"},
        {"photo": "33333333-3333-4333-8333-333333333333", "caption": "หลังทดสอบ"}
      ]
    }
  }]
}
```

นิยาม local array มี `items: {type:"object", fields:{photo:{type:"image",
required:true}, caption:{type:"string"}}}`; ผู้ใช้ไม่ส่ง childIds หรือคำสั่งทำซ้ำ
URL/base64 ยังคงเข้ากระบวนการ upload/เตรียมภาพเดิม แล้วอ้าง resource ID
ไม่เพิ่มรูปแบบส่งภาพดิบใน generation request

#### ผลหลังประกอบและกฎความผิดพลาด

- ได้หัวข้อครั้งเดียว → รูป/คำบรรยายรายการ 0 → รูป/คำบรรยายรายการ 1 → หมายเหตุ
- `[]` ลบเฉพาะช่วงทำซ้ำ ไม่สร้างช่องว่าง/กรอบของชุด; cell, padding และข้อความ
  คงที่ยังอยู่ หากทั้ง cell ว่างใช้กฎ empty-cell เดิม ไม่ลบ cell/แถวเอง
- ไม่ส่ง key: required มาก่อน default; ถ้า optional ไม่มี default ใช้ []
  default ต้องผ่าน schema เดียวกัน; ส่ง null หรือชนิดผิดไม่แปลงเงียบ ๆ
- item ผิดชนิด/ขาด required ทำให้ request ไม่ผ่าน พร้อม path เช่น
  `content[0].data.evidenceList[1].photo`; unknown keys ใช้ warning/ignore เดิม
  ไม่เพิ่มกฎข้าม item ใน slice นี้ ส่วนภาพอ้างถูกชนิดแต่เตรียมไม่ได้ใช้ image
  warning/กรอบว่างเดิม รวมถึง upload ownership/resource checks เดิม
- clone แต่ละ node/inline ต้องมี ID ไม่ชนกับ static nodes, row repeats หรือ cell
  repeats อื่น โดยอาศัย content instance, repeat ID, item index และ source ID
  sourceMap คง sourceId/contentIndex/format/itemIndex พร้อม repeatId สำหรับชุดใหม่
  ไม่แก้ต้นฉบับ; index เป็นตำแหน่งการสร้างครั้งนี้ ไม่สัญญา identity คงเดิมเมื่อ reorder
- ขยายเป็น TextBlock/Image ปกติก่อนจัดหน้า; ไม่มีกรอบกลุ่ม ไม่มี gap เพิ่ม
  ข้อความแบ่งที่บรรทัด รูปย้ายทั้งกรอบ และ allowBreak/oversize/padding ใช้กฎเดิม
  ไม่บังคับรูปกับ caption อยู่หน้าเดียวกัน และไม่ขยาย schema สำหรับ frontend

#### เกณฑ์สำหรับแผนลงมือถัดไป

1. Core contract: model 10/nonempty item schema/item image/cell repeat ownership
   และปฏิเสธ nesting; รุ่น 4–9 ไม่เปลี่ยนการรับ/ปฏิเสธข้อมูลเดิม
2. Binding: 0/1/หลายรายการ, static siblings, หลาย cell/หลาย content instances,
   global/local/item ชื่อซ้ำ, defaults/errors, IDs/sourceMap และ input immutability
3. Export: ข้อความไทยยาว หลายรูปและหลายหน้าใน ordinary/merged cell,
   ไม่มีหาย/ซ้ำ; ของเดิม row repeats, links, TOC และ headers ยังผ่าน
4. Service: current→version→load เก็บ image child และ cellRepeats ครบ,
   เปลี่ยน draft แล้ว version เก่ายังคงเดิม; finalized upload→job→PDF
   และ resource reuse/error paths ผ่าน real DB ไม่มี skip
5. ส่งมอบ: ใช้ packed Core ใน Linux/amd64, PDF ตัวอย่างหนึ่งชุดให้เจ้าของดู;
   ค่อยเพิ่มรุ่นเมื่อใช้ได้และตรวจผ่าน ไม่เลื่อน release อัตโนมัติ

นี่เป็นลำดับผลตรวจที่แผนลงมือต้องครอบคลุม ยังไม่ใช่ task execution plan
ก่อนลงมือให้ตรวจว่าข้อเสนอ childTemplateIds, ขอบเขตหนึ่ง repeat/cell และการกัน
repeat ซ้อนตรงความต้องการ แล้วแตกงาน Core contract/binding → Service/PDF proof
อยู่ในห้องนี้ได้ ไม่ต้องสร้างห้อง/ทะเบียนเพียงเพื่อพัฒนา

### Array และ Area ทำหน้าที่ต่างกัน

- `image` รับภาพเดียว ไม่เพิ่มรูปแบบ multiple ให้ชนิด image
- `array` เป็นรายการข้อมูล ต้องนิยามตัวแปรลูกอย่างน้อยหนึ่งตัว เช่น photo: image
  และ caption: string; ไม่ได้หมายความว่าข้อมูลจริงต้องมีอย่างน้อยหนึ่งรายการ
- เคสจริงคือรายการหลักมีหัวข้อ/รายละเอียด และรายการภาพต่อท้ายจำนวนไม่แน่นอน
  จึงต้องออกแบบ scope ของรายการลูกและการทำซ้ำเมื่อถึงพาร์ตนี้
- `area` เป็นพื้นที่รับรายการโครงย่อยในแม่แบบ ชื่อ key เช่น a/b ผู้สร้างตั้งเอง
  ต้องกำหนดตำแหน่งและโครงย่อยที่รองรับ; ข้อมูลที่ส่งเข้ามาเป็นรายการตามลำดับ
- แต่ละรายการระบุ format เพื่อเลือกโครงย่อย และ data สำหรับชุดตัวแปรของโครงนั้น
  key ที่ครอบรายการบอกพื้นที่ปลายทางอยู่แล้ว ไม่ต้องระบุปลายทางซ้ำในแต่ละรายการ

ตัวอย่าง payload เฉพาะค่าตัวแปรเชิงแนวคิด ไม่ใช่ request/API schema ที่เผยแพร่แล้ว:

```json
{
  "a": [{ "format": "description", "data": { "text": "รายละเอียดการทดสอบ" } }],
  "b": [{ "format": "evidence", "data": { "photo": "<resourceId>", "caption": "ผลการทดสอบ" } }]
}
```

### กฎที่ตกลงแล้ว

| เรื่อง | ข้อตกลง |
| --- | --- |
| นิยาม area | ต้องรองรับโครงย่อยอย่างน้อยหนึ่งแบบ และทุกโครงที่อ้างต้องหาเจอ; ไม่ให้ประกาศเปล่า |
| นิยามผิด | หน้าบ้านอนาคตแสดงสถานะผิด; หลังบ้านตรวจเอง คืน feedback และไม่สร้างเอกสารจากนิยามที่ผิด |
| API ส่งรายการว่าง | `[]` ใช้ได้ ไม่สร้างเนื้อหาในพื้นที่นั้น; ไม่ใช่ความผิดของนิยาม area |
| API ส่งรายการใช้ไม่ได้ | format ไม่รองรับหรือ data ของรายการไม่ผ่าน ให้ข้ามรายการนั้น ยังสร้างเอกสารจากส่วนที่ใช้ได้ พร้อม warning ระบุ area/ลำดับ/สาเหตุ |
| ขอบเขต warning | กฎข้ามนี้ใช้กับรายการใน area ไม่ได้เปลี่ยน validation ของ request ทั้งก้อนหรือปัญหาโครงแม่แบบให้เป็น warning |
| ไม่ส่ง key | ใช้กฎ required/default ที่มีอยู่; ต้องแยกจากการส่งรายการว่าง |
| ชื่อกับ identity | ภายในอ้างด้วย ID; API ใช้ key ที่ผู้สร้างตั้ง อ่านตามเวอร์ชันที่เลือก ไม่ให้การเปลี่ยน key ของต้นฉบับทำลาย reference ภายใน |
| เวอร์ชัน | area โครงย่อย และนิยามตัวแปรต้องมาจากชุดเวอร์ชันที่ล็อกไว้ ไม่อ่านค่าปัจจุบันมาปน |
| ความกว้าง | area ไม่มีความกว้างอิสระ ใช้เต็มพื้นที่ภายในตำแหน่งที่วาง; การแบ่ง Columns ถ้ามีเป็นหน้าที่โครงย่อยและต้องอยู่ในขอบเขตที่ตำแหน่งนั้นอนุญาต |
| ข้อจำกัดตำแหน่ง | โครงย่อยต้องไม่พา Columns/ตารางซ้อนเข้ามาใน cell ที่ยังไม่รองรับ; ตรวจชนิดเนื้อหาหลังขยายด้วย |
| ความลึกเริ่มต้น | โครงย่อยยังไม่ประกาศ area ซ้อนต่อ; ไม่เปิด arbitrary nesting |

### ข้อเสนอและเรื่องที่ยังเปิดอยู่

ข้อเสนอ: ให้ area อ้างโครงย่อยที่ใช้ร่วมกันได้ แทนการทำสำเนานิยามซ้ำทุกพื้นที่
ยังต้องออกแบบ schema จริง การอ้าง ID/key จุดทำซ้ำ และขอบเขต instance ให้ครบ
พร้อมตัวอย่างแม่แบบ → request → โครงหลังประกอบ และกรณีข้ามรายการพร้อม warning
การประเมินพื้นที่ไม่พอ การย่อ/ปฏิเสธ/ข้ามเมื่อวางไม่ลง และภาพร่าง feedback บน
หน้าบ้านถูกพักไว้ ยังไม่มีนโยบายที่อนุมัติสำหรับ area; ไม่ตีความกฎข้อมูลผิด
เป็นคำสั่งให้ข้าม layout error และไม่ยกเลิกข้อเสนอ oversize ของ direct-cell slice

## เรื่องที่ยังไม่ล็อกและเกณฑ์ก่อนกาง roadmap

ยังเปิดอยู่ในชุดแรก: รายละเอียดสัญญาลูก TextBlock/Image ภายในเซลล์ กติกาขนาด
และภาพที่ใหญ่กว่าพื้นที่หน้า ส่วนผลจัดหน้าสำหรับ frontend/คำสั่งแก้ไขเลื่อนไปงานหน้าบ้าน
ส่วน node กลุ่มและความลึกของโครงย่อยซ้อนเลื่อนไว้ตามขอบเขตพาร์ต 1
เรื่องเหล่านี้ไม่ขัดขวางการร่าง แต่ต้องตัดสินเฉพาะส่วนที่จะลงมือก่อนวางแผนพัฒนา

DB การจัดคิวหลายงานพร้อมกัน หน้าบ้านจริง undo/redo และ DOCX เป็นหัวข้อแยก
การออกแบบนี้อาจระบุสิ่งที่หัวข้อเหล่านั้นต้องใช้ แต่ยังไม่เปลี่ยนระบบเหล่านั้น
ความเหมือนระหว่างหน้าบ้านกับ PDF เป็นเป้าหมายที่ต้องทดสอบ ไม่ได้เกิดขึ้น
อัตโนมัติเพียงเพราะใช้โครงเดียวกัน

ก่อนกาง roadmap ของชุดแรก ต้องมีขอบเขตที่เจ้าของเลือก ตัวอย่างโครงและข้อมูล
หนึ่งชุด กติกาแม่–ลูก/ขนาด/การแบ่งหน้าที่เกี่ยวข้อง ขอบเขตของเดิมที่ต้องรักษา
และตัวอย่างผลที่ถือว่าผ่าน ส่วนที่ยังไม่เลือกให้ระบุว่าเลื่อนไว้ ไม่บังคับแก้
