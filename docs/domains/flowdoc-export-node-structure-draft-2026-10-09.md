## เป้าหมายของร่าง

ออกแบบโครงเอกสารที่ใช้สร้าง PDF ต่อจากรุ่น 0.1.5 และเปิดทางให้หน้าบ้าน
อ้างถึงและแก้เนื้อหาเดียวกันได้ในอนาคต เริ่มจากหน้าที่ของ node แล้วค่อยตกลง
การอยู่ภายในกัน ขนาด การไหล ตัวแปร และความเข้ากันได้ แบ่งคุยเป็นพาร์ตย่อย
ได้ตามความจำเป็น โดยยังไม่กำหนดรุ่นส่งมอบหรือลำดับลงมือทำเป็น roadmap

โจทย์ที่ต้องเผื่อคือเอกสาร UAT หรือเอกสารเล่มยาวที่ผู้สร้างกำหนดรูปแบบไว้
แต่ผู้ใช้ส่งข้อมูลและลำดับโครงย่อยได้ ภายในเซลล์อาจต้องมีข้อความหลายส่วน
และรูปภาพร่วมกัน รูปแบบนี้เป็นเป้าหมายที่จะออกแบบ ไม่ใช่ความสามารถที่รองรับแล้ว

## หลักที่ตกลงใช้เป็นทิศทาง

1. ออกแบบเผื่อหน้าบ้าน แต่ยังไม่สร้างหน้าบ้านในรอบออกแบบนี้
2. แยกโครงเอกสาร ผลคำนวณจัดหน้า และสถานะการแก้ไขบนหน้าบ้านออกจากกัน
3. การแก้เนื้อหาของ node เดิมควรรักษา identity ของมันไว้ การคัดลอกหรือทำซ้ำ
   เป็นอีก instance ต้องมี identity แยก โดยความสัมพันธ์กับต้นแบบต้องอธิบายได้
4. การข้ามหน้าไม่ควรสร้าง authored node ใหม่เพียงเพราะพื้นที่กระดาษหมด
   ส่วนที่แสดงแต่ละหน้าต้องอ้างกลับ node และช่วงเนื้อหาต้นทางได้
5. แยกค่าที่ผู้สร้างกำหนดจากค่าที่ layout คำนวณ เช่น ความสูงตามเนื้อหา
   ไม่เขียนทับเป็นความสูงตายตัวของต้นฉบับ
6. ทุกพาร์ตต้องตอบว่า “ถ้ามีหน้าบ้านมาแก้สิ่งนี้ จะอ้างถึงและเปลี่ยนมันอย่างไร”
   การแก้เฉพาะส่วนเป็นเป้าหมายออกแบบ ยังไม่ใช่คำรับรอง incremental layout
   หรือความลื่นขณะพิมพ์ และยังไม่เลือก revision/cache protocol

| --- | --- | --- |

| ผลจัดหน้า | หน้า ตำแหน่ง ขนาดจริง ส่วนต่อเนื่อง และข้อมูลเชื่อมกลับต้นทาง | ไม่เปลี่ยนความหมายหรือ identity ของต้นฉบับเพื่อแบ่งหน้า |

รูปแบบข้อมูลจริงและขอบเขตการคำนวณยังต้องตกลงในแต่ละพาร์ต

## คำที่ต้องใช้ให้ตรงกัน

อ้างอิง [Product terminology](flowdoc-product-terminology.md) โดยร่างนี้กำหนดขอบเขตดังนี้:

- `Core runtime node` — define: องค์ประกอบในโครงเอกสารของ Core ไม่ใช่ Node ของ Project Control
- โครงเอกสาร — split: แม่แบบที่ยังมีตัวแปร กับเอกสารที่ผูกข้อมูลแล้ว ต้องระบุว่าพูดถึงฝั่งไหน
- หน้าบ้าน — split: เครื่องมือสร้างแม่แบบ กับหน้ากรอกข้อมูลในแม่แบบ เป็นคนละขอบเขตสิทธิ์และคำสั่ง ยังไม่เลือกทำอย่างใดในรอบนี้
- กล่อง — context-only: ต้องระบุว่าเป็นกรอบเนื้อหา กรอบเซลล์ หรือกรอบ selection ก่อนแปลงเป็นกติกา
- container — context-only: เป็นชื่อแนวคิดสำหรับจัดกลุ่ม ยังไม่ยืนยันว่าจะเพิ่มชนิด node นี้
- เวอร์ชัน — split: รุ่นซอฟต์แวร์ รุ่นโมเดล และเวอร์ชันแม่แบบ ไม่ใช้แทนกัน

## พาร์ตที่จะคุย

ตารางนี้เป็นหัวข้อออกแบบ ไม่ใช่ขั้นลงมือพัฒนาหรือข้อผูกมัดว่าต้องสร้างทุกอย่าง

| พาร์ต | เรื่องที่ต้องตกลง | สิ่งที่ควรได้เมื่อคุยจบ |
| --- | --- | --- |
| 1 หน้าที่ของ node | อะไรเป็นเนื้อหา อะไรจัดกลุ่ม อะไรจัดวาง อะไรเป็นผลที่ระบบสร้าง | รายการชนิดที่จำเป็น พร้อมหน้าที่และตัวอย่าง |
| 2 แม่และลูก | ชนิดลูกที่รับได้ จำนวน/ความลึก ลำดับ และความหมายของเพิ่ม ย้าย คัดลอก ลบ | ตารางความสัมพันธ์และกติกา identity |
| 3 ขนาดและพื้นที่ | ความกว้าง/สูง ค่าคงที่/ตามเนื้อหา padding และระยะระหว่างลูก | กติกาคำนวณที่แยกค่าต้นฉบับจากผลจริง |
| 4 การไหลและข้ามหน้า | จุดแบ่ง สิ่งที่ต้องอยู่ด้วยกัน กรอบต่อเนื่อง หัวซ้ำ และกรณีวางไม่ลง | ตัวอย่างก่อน/หลังแบ่งหน้าและผลล้มเหลวที่ชัดเจน |
| 5 ตัวแปรและการทำซ้ำ | scope การผูกข้อมูล ตัวตนของ instance และการอ้างกลับโครงย่อย | ตัวอย่างข้อมูลเข้าและโครงหลังประกอบ รวมความหมายเมื่อแก้จากหน้าบ้าน |
| 6 ใช้กับของเดิม | รูปแบบเดิมอ่านอย่างไร อะไรเปลี่ยน รุ่นโมเดลและการย้ายถ้าจำเป็น | ขอบเขต compatibility และตัวอย่างตรวจรับ |

แต่ละพาร์ตแบ่งย่อยได้ บันทึกในเอกสารนี้ก่อน พร้อมแยก “ตกลงแล้ว”
“ข้อเสนอ” และ “ยังเปิดอยู่” ไม่ต้องสร้างเอกสารใหม่ทุกครั้งที่คุย

## พาร์ต 1 ขอบเขตเริ่มต้นที่ตกลงแล้ว

เจ้าของยืนยันให้ค่อยเป็นค่อยไป: ออกแบบให้หนึ่ง cell มี TextBlock และ Image
หลายชิ้นเรียงจากบนลงล่างเป็นลูกโดยตรงก่อน แต่ละชิ้นเป็น node ของตัวเอง
ตัวอย่างคือ “ข้อความอธิบาย → รูปหลักฐาน → คำบรรยาย” โดยคำบรรยายใช้ TextBlock
ข้อนี้เป็นขอบเขตการออกแบบที่ยอมรับแล้ว ยังไม่ใช่การรองรับภาพในเซลล์ของรุ่นปัจจุบัน
หรือการอนุมัติ schema และ implementation ทั้งชุด

รอบแรกไม่เพิ่ม node กลุ่มหรือฟิลด์สำรองสำหรับสิ่งที่ยังไม่มีการใช้งานจริง
ไม่ตั้งสมมติฐานว่า cell มีได้เพียง TextBlock เดียวหรือลูกทุกตัวต้องเป็นข้อความ
การเพิ่มชนิดลูกภายหลังยังอาจต้องขยายสัญญาข้อมูลและตรวจความเข้ากันได้

### กรณีอนาคตที่เลื่อนไว้

หนึ่ง cell อาจมีโครงย่อยหลายชุด เช่น “หลักฐาน A” และ “หลักฐาน B”
โดยแต่ละชุดมีข้อความ รูป และตัวแปรของตัวเอง เจ้าของยืนยันว่ามีกรณีใช้งานจริง
แต่เลื่อนการเรียกโครงย่อยภายใน cell ตัวแปรเฉพาะชุด การทำซ้ำชุด และการจัดการ
ทั้งกลุ่มไว้ก่อน รวมถึงยังไม่เพิ่ม container ซ้อนทั่วไป
การเลื่อนนี้ไม่ยกเลิกความสามารถโครงย่อยหรือข้อมูลซ้ำที่มีอยู่ในฐานเดิม

แยกความหมายไว้ว่าโครงย่อยเป็นแบบที่นำมาใช้ ส่วนกลุ่ม node เป็นผลหลังประกอบ
เมื่อกลับมาทำกรณีนี้จึงค่อยตัดสินว่าจะรักษาขอบเขตกลุ่มไว้หรือขยายลูกมาต่อกัน
ยังไม่กำหนด identity ของกลุ่ม กติกาการย้ายทั้งชุด หรือการรักษาชุดเมื่อข้ามหน้า

### ประเด็นที่คุยต่อ

ยังต้องตกลงหน้าที่ของ node ที่เกี่ยวข้องและรายละเอียดแม่–ลูก ขนาด ระยะห่าง
และการแบ่งหน้า โดยใช้ตัวอย่างลูกหลายชิ้นข้างต้นเป็นโจทย์หลัก
ไม่ถือว่าพาร์ต 1 ทั้งหมดเสร็จเพียงเพราะเลือกขอบเขตเริ่มต้นนี้

## เรื่องที่ยังไม่ล็อกและเกณฑ์ก่อนกาง roadmap

ยังเปิดอยู่ในชุดแรก: รายละเอียดสัญญาลูก TextBlock/Image ภายในเซลล์ กติกาขนาด
และภาพที่ใหญ่กว่าพื้นที่หน้า รูปแบบผลจัดหน้าที่ส่งให้หน้าบ้าน และคำสั่งแก้ไขที่จำเป็น
ส่วน node กลุ่มและความลึกของโครงย่อยซ้อนเลื่อนไว้ตามขอบเขตพาร์ต 1
เรื่องเหล่านี้ไม่ขัดขวางการร่าง แต่ต้องตัดสินเฉพาะส่วนที่จะลงมือก่อนวางแผนพัฒนา

DB การจัดคิวหลายงานพร้อมกัน หน้าบ้านจริง undo/redo และ DOCX เป็นหัวข้อแยก
การออกแบบนี้อาจระบุสิ่งที่หัวข้อเหล่านั้นต้องใช้ แต่ยังไม่เปลี่ยนระบบเหล่านั้น
ความเหมือนระหว่างหน้าบ้านกับ PDF เป็นเป้าหมายที่ต้องทดสอบ ไม่ได้เกิดขึ้น
อัตโนมัติเพียงเพราะใช้โครงเดียวกัน

ก่อนกาง roadmap ของชุดแรก ต้องมีขอบเขตที่เจ้าของเลือก ตัวอย่างโครงและข้อมูล
หนึ่งชุด กติกาแม่–ลูก/ขนาด/การแบ่งหน้าที่เกี่ยวข้อง ขอบเขตของเดิมที่ต้องรักษา
และตัวอย่างผลที่ถือว่าผ่าน ส่วนที่ยังไม่เลือกให้ระบุว่าเลื่อนไว้ ไม่บังคับแก้
ทุกพาร์ตจนสมบูรณ์เพื่อเริ่มงานชุดเล็ก

สถานะปัจจุบัน: ร่างที่บันทึกขอบเขตเริ่มต้นของพาร์ต 1 แล้ว คุยรายละเอียดต่อได้ ยังไม่มี roadmap
หรือคำสั่งให้เปลี่ยนพฤติกรรมผลิตภัณฑ์จากเอกสารนี้
