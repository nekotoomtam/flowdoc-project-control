# ข้อตกลงการออกแบบคลังฟอนต์ FlowDoc

วันที่ 2026-10-16 — เจ้าของทบทวนฉบับรวมและให้จัดทำแผนพัฒนาแล้ว

ลำดับงานและเกณฑ์ตรวจอยู่ใน [แผนพัฒนาตามช่วง](flowdoc-font-library-development-plan-2026-10-16.md).

## Authority Boundary

Owner: FlowDoc Project Control. บทบาท Planning Partner / Documentation Synthesizer.
เอกสารนี้รวบรวมข้อตกลงที่เจ้าของยืนยันในบทสนทนา เป็นข้อกำหนดการออกแบบ
ไม่ใช่สัญญา runtime ที่พัฒนาแล้ว แผนดำเนินงาน migration หรือหลักฐานรับรองระบบ.
งานเอกสารเป็น single-room ตามคำขอผู้ใช้; execution/Phase/Checklist IDs ไม่เกี่ยวข้อง.
ไม่มีการเปลี่ยน Core, Service, Editor, ฐานข้อมูล, draft หรือคลังไฟล์ฟอนต์ในงานนี้.
รายละเอียดสัญญาที่ปิดในช่วง 0 อยู่ในแผนที่อ้างข้างบน; ผลตรวจ runtime ต้องได้จากช่วงพัฒนาจริง.
อ่านเอกสารนี้เมื่อทำงานคลังฟอนต์ ไม่เพิ่มเป็นเอกสารเริ่มต้นบังคับของ FlowDocMake.

## 1 เป้าหมายและขอบเขตช่วงแรก

ทุกเอกสารใช้ไฟล์จากคลังของระบบ เพื่อควบคุมตัวตน รุ่น และไฟล์ที่ใช้สร้าง PDF.
ช่วงแรกผู้ดูแลระบบนำเข้าฟอนต์จาก Google Fonts แล้วจึงเปิดให้ผู้ใช้เลือก.
เจ้าของยืนยันให้เริ่มด้วยเครื่องมือผู้ดูแล; หน้าจอจัดการคลังเลื่อนไปภายหลัง.
รับเฉพาะ TTF แบบคงที่; custom font จากผู้ใช้, OTF และ variable font อยู่นอกช่วงแรก.
ไม่ดึงฟอนต์จาก Google Fonts หรือเครื่องผู้ใช้ระหว่างสร้างเอกสาร.
ไม่แทนฟอนต์ เลือกน้ำหนักใกล้เคียง หรือสร้างตัวหนา/ตัวเอียงจำลองอัตโนมัติ.
เรื่อง style เส้น/กรอบและการวางแบบฟอร์มเป็นคนละขอบเขต ยังไม่รวมในข้อตกลงนี้.

การตรึงไฟล์ฟอนต์ช่วยรักษาผลจัดหน้า แต่ไม่รับรองว่า PDF จะเหมือนเดิมทุกไบต์
เมื่อรุ่นตัวสร้างเปลี่ยน จึงต้องตรวจย้อนกลับถึงรุ่นตัวสร้างที่ใช้ด้วย.

## 2 โครงสร้างและความหมายของข้อมูล

ชื่อด้านล่างเป็นแนวคิดสำหรับออกแบบ ไม่ใช่ชื่อ table หรือ API ที่กำหนดแล้ว.

| ส่วน | ข้อมูลที่ต้องมี | กฎสำคัญ |
| --- | --- | --- |
| ตระกูลฟอนต์ | รหัสถาวร ชื่อแสดง ชื่อภายใน ผู้จัดทำ/แหล่งที่มา | ชื่อแสดงไม่ใช่ตัวตัดสินว่าเป็นตระกูลเดียวกัน |
| รุ่นในคลัง | รหัสรุ่น ตระกูล ชุดรูปแบบ ข้อมูลต้นทาง ใบอนุญาต ผลตรวจ สถานะ วันที่ออกใช้ | หนึ่งรุ่นคือชุดไฟล์ที่ตรวจและออกใช้พร้อมกัน |
| รูปแบบภายในรุ่น | น้ำหนักที่อนุมัติ ปกติ/เอียง และรหัสไฟล์ | การจับคู่แต่ละน้ำหนักและรูปแบบต้องไม่กำกวม |
| ไฟล์จริง | รหัสไฟล์ hash ชนิด ขนาด ตำแหน่งเก็บ รุ่นในไฟล์ และ metadata ที่อ่านได้ | ไม่เขียนทับไฟล์เดิม หลายรุ่นอ้างไฟล์เดียวกันได้ |
| ความสามารถของไฟล์ | ชุดตัวอักษรที่รองรับ น้ำหนัก รูปแบบ และผลตรวจที่เกี่ยวข้อง | แยกข้อมูลที่อ่านได้จากข้อสรุปที่อนุมัติใช้ |
| ประวัติการจัดการ | ผู้ทำ เวลา การกระทำ ผลตรวจซ้ำ การตัดสินใจ และเหตุผล | ตรวจย้อนกลับการนำเข้า อนุมัติ ออกใช้ และเปลี่ยนสถานะได้ |

เก็บแหล่งที่มาของไฟล์และ metadata พร้อมรุ่น/จุดอ้างอิงต้นทางที่ตรวจได้
และใบอนุญาตที่ใช้กับชุดนั้น. การใช้ไฟล์ร่วมกันไม่ทำให้ประวัติแหล่งที่มาหายไป.
รุ่นในคลังแยกจากเลขรุ่นภายในแต่ละไฟล์ ไม่บังคับให้ทุกไฟล์มีเลขรุ่นภายในเท่ากัน.

## 3 น้ำหนักสามค่า

| ค่า | ความหมายและที่มา |
| --- | --- |
| น้ำหนักจากไฟล์ | ค่าที่อ่านได้จริง เช่น OS/2.usWeightClass เก็บโดยไม่แก้ต้นฉบับ |
| น้ำหนักจากต้นทาง | ค่าที่ Google Fonts ประกาศ พร้อมแหล่งอ้างอิง/รุ่น metadata; ถ้าไม่มีให้ระบุว่าไม่มี |
| น้ำหนักที่อนุมัติในคลัง | ค่าสำหรับเลือกใช้ ซึ่งผู้ดูแลตรวจและจับคู่กับไฟล์ในรุ่นนั้นแล้ว |

ค่าตรงกันใช้เป็นข้อเสนอได้; ค่าขัดกันต้องมีข้อสรุปก่อนออกใช้ ไม่เดาจากชื่อไฟล์.
สำหรับชุด Google Fonts ใช้ค่าที่ต้นทางประกาศเป็นค่าตั้งต้นในการพิจารณา
หลังยืนยันว่า metadata ตรงกับไฟล์ชุดที่นำเข้าจริง ไม่ใช่แค่ชื่อเหมือนกัน.
เก็บเหตุผลและผู้อนุมัติเมื่อค่าต่างกัน ไม่เขียนค่าทับไฟล์เพื่อให้ตัวเลขตรงกัน.
การเลือกน้ำหนัก 100 หมายถึงเลือกไฟล์ที่จับคู่ไว้ ไม่ใช่ดัดไฟล์น้ำหนักอื่นให้บางลง.

## 4 ชุดขั้นต่ำและการรักษารุ่น

- ทุกรุ่นต้องมีรูปแบบปกติ น้ำหนักที่อนุมัติในคลัง 400 หนึ่งรายการก่อนออกใช้.
- ตัวหนา ตัวเอียง ตัวหนาเอียง และน้ำหนักอื่นเป็นตัวเลือกเพิ่มตามที่ระบบรองรับ.
- การมีตัวหนาและตัวเอียงแยกกัน ไม่ถือว่ามีตัวหนาเอียง ต้องมีการจับคู่โดยตรง.
- ชุดที่ไม่มีปกติ 400 เก็บเป็นชุดเตรียมได้ แต่ยังออกใช้ไม่ได้.
- รูปแบบทุกตัวที่ประกาศในชุดต้องผ่านเกณฑ์ตรวจ ไม่จำเป็นต้องมีครบสี่รูปแบบ.
- รุ่นเตรียมแก้ได้; หลังออกใช้ห้ามเปลี่ยนสมาชิก ไฟล์ หรือการจับคู่ที่กำหนดผลใช้งาน.
- เพิ่มรูปแบบ เปลี่ยนไฟล์ หรือเปลี่ยนการจับคู่ภายหลัง ต้องออกเป็นรุ่นใหม่.
- รุ่นใหม่อ้างไฟล์เดิมได้เมื่อเนื้อไฟล์ตรงกัน ไม่ต้องเก็บไฟล์ซ้ำ.

## 5 ขั้นตอนนำเข้าและตรวจซ้ำ

1. รับเข้าพื้นที่เตรียม เก็บต้นฉบับ ที่มา และใบอนุญาต ยังไม่ให้ผู้ใช้เลือก.
2. อ่านและตรวจไฟล์จริง: ชนิด ความเป็นฟอนต์คงที่ โครงสร้าง ชื่อ รุ่น น้ำหนัก
   รูปแบบ และตัวอักษรที่รองรับ; ตรวจซ้ำด้วย hash.
3. ยืนยันตระกูลและจัดการความขัดแย้งของ metadata รวมถึงน้ำหนักสามค่า.
4. ประกอบรุ่น ระบุรูปแบบและไฟล์ที่จะออกใช้ร่วมกัน พร้อมความต่างจากรุ่นก่อน.
5. ตรวจชุดตามข้อ 8 ผูกผลตรวจกับชุดและ hash ที่ตรวจจริง.
6. ผู้ดูแลยืนยันออกใช้ทั้งชุด จึงเปิดให้เลือกในเอกสารใหม่.

| สิ่งที่พบ | การจัดการ |
| --- | --- |
| เนื้อไฟล์เหมือน แม้ชื่อไฟล์ต่าง | อ้างไฟล์เดิม ไม่เก็บซ้ำ |
| รูปแบบเดียวกันแต่เนื้อไฟล์ต่าง | ตรวจเป็นการเปลี่ยนไฟล์ และออกเป็นรุ่นใหม่เมื่อจะใช้แทนรุ่นที่ออกใช้แล้ว |
| ทั้งชุดและข้อมูลออกใช้เหมือนรุ่นที่มีแล้ว | แจ้งรายการเดิม ไม่สร้างรุ่นใหม่อัตโนมัติ |
| ชื่อตระกูลเหมือน แต่ตัวตน/ข้อมูลขัดกัน | ให้ผู้ดูแลตรวจ ไม่รวมจากชื่ออย่างเดียว |

การพบไฟล์เดิมไม่ข้ามการตรวจความถูกต้องของการจับคู่ ที่มา และใบอนุญาตของชุดใหม่.

## 6 การอ้างฟอนต์ในเอกสารและ PDF

แต่ละ TextStyle อ้างรหัสรุ่นฟอนต์ในคลัง น้ำหนักที่อนุมัติ และปกติ/เอียง
พร้อมขนาดและระยะบรรทัดของ style นั้น. ตระกูลและชื่ออ่านย้อนจากรุ่นได้
ไม่ต้องคัดข้อมูลคลังทั้งหมดหรือเก็บไฟล์ฟอนต์ลงในเอกสารซ้ำ.

ระบบเสนอรุ่นเริ่มต้นได้ แต่เมื่อเลือกต้องบันทึกรหัสรุ่นจริง ไม่เก็บคำว่า latest
แล้วค้นใหม่ตอนสร้าง PDF. เอกสารเดียวใช้หลาย style/หลายตระกูลได้.
เปลี่ยนรุ่นเริ่มต้นหรือเพิ่มรุ่นในคลังไม่อัปเกรดเอกสารเดิมอัตโนมัติ.
การวัดข้อความและฝัง PDF ต้องใช้ไฟล์เดียวกัน ตรวจ hash และบันทึกย้อนกลับได้
ว่ารอบนั้นใช้รุ่น รูปแบบ ไฟล์ และตัวสร้างใด. ผลตรวจผูกกับ revision และข้อมูลรอบนั้น.

## 7 การรองรับ Sarabun เดิม

สร้างรุ่นในคลังสำหรับชุดเดิมจากไฟล์ที่ตรวจยืนยันได้ ไม่ใช้ชื่อ Sarabun อย่างเดียว.
รองรับการอ่านสัญญาเดิมและจับคู่กับรุ่นชุดเดิมดังนี้:

| ค่าเดิม | การจับคู่ใหม่ |
| --- | --- |
| normal และปกติ | 400 ปกติ |
| bold และปกติ | 700 ปกติ |
| normal และเอียง | 400 เอียง |
| bold และเอียง | 700 เอียง |

ไม่เขียนข้อมูลใหม่ทับเมื่อเปิดอ่าน. การแปลงถาวรต้องเป็น revision/รุ่นใหม่
ตามประเภทเอกสาร โดยรักษาต้นฉบับและตรวจผลเทียบก่อน.
ถ้ายืนยันชุดไฟล์ที่เอกสารเก่าใช้ไม่ได้ ให้เป็นงานตรวจเพิ่ม ไม่เดาว่าใช้รุ่นปัจจุบัน.
การตรึงฟอนต์เดิมไม่ใช้แทนหลักฐานว่าการเปลี่ยน renderer ไม่กระทบผลจัดหน้า.

## 8 เกณฑ์ตรวจและออกใช้

พร้อมใช้หมายถึงผ่านตามรูปแบบและขอบเขตที่ประกาศ ไม่ใช่รองรับทุกข้อความ.

| กลุ่มตรวจ | เกณฑ์ผ่าน |
| --- | --- |
| ไฟล์ | เป็น TTF คงที่ อ่านโครงสร้างได้ hash ตรงกับไฟล์ที่เก็บ |
| ชุดรุ่น | มีปกติ 400 ทุกน้ำหนัก/รูปแบบจับคู่ไฟล์ได้แน่นอน ไม่มีรายการชนกัน |
| ข้อมูลและที่มา | น้ำหนักสามค่าชัดเจน ความขัดแย้งมีข้อสรุป ที่มาและใบอนุญาตผ่านการตรวจ |
| ตัวอักษร | ตรวจ coverage และข้อความจริงตามขอบเขตที่ประกาศ เช่น ไทย สระ/วรรณยุกต์ อังกฤษ ตัวเลข เครื่องหมาย |
| การจัดหน้าและ PDF | วัด/ตัดบรรทัด/ระยะบรรทัด/ภาพ PDF ผ่านสำหรับทุกรูปแบบที่ประกาศ ใช้ไฟล์เดียวกันทั้งวัดและฝัง ไม่มีการแทนเงียบ ๆ |
| การออกใช้ | ผลตรวจตรงกับชุดและ hash ปัจจุบัน ผู้ดูแลยืนยันออกใช้ทั้งชุด |

ใช้หน้าทดสอบสั้นที่เป็นตัวแทน ไม่ต้องสร้างเอกสารเล่มใหญ่ทุกครั้ง.
ใช้ผลเดิมซ้ำได้เมื่อไฟล์และเงื่อนไขที่เกี่ยวข้องไม่เปลี่ยน; renderer เปลี่ยน
ต้องประเมินผลกระทบและตรวจใหม่ตามส่วนที่ได้รับผล.
เปลี่ยนไฟล์/การจับคู่ให้ยกเลิกผลผ่านของส่วนที่ได้รับผลและตรวจความครบของชุดใหม่.
ถ้ารูปแบบหนึ่งยังไม่ผ่าน ทั้งรุ่นยังออกใช้ไม่ได้; การตัดรูปแบบออกต้องแก้ชุดเตรียม
และตรวจตามรายการใหม่ให้ครบ. ก่อนสร้าง PDF ยังต้องตรวจข้อความจริงทุกครั้ง.

## 9 สถานะและการจัดการคลัง

สถานะเป็นของรุ่นในคลัง การตรวจผ่านกับการเปิดให้เลือกเป็นคนละขั้น.

| สถานะ | สิ่งที่ทำได้ | การใช้ในเอกสาร |
| --- | --- | --- |
| เตรียม | เพิ่ม/ถอดรูปแบบ เปลี่ยนไฟล์ จัดข้อมูลและการจับคู่ | ยังไม่เปิดให้เลือก |
| รอตรวจ | ตรวจชุดที่ตรึงระหว่างตรวจ หากแก้ให้ถอนกลับเตรียม | ยังไม่เปิดให้เลือก |
| ต้องแก้ | ดูเหตุผล แก้ไฟล์/ข้อมูล ส่งตรวจใหม่ | ยังไม่เปิดให้เลือก |
| พร้อมออกใช้ | ดูผลและยืนยันออกใช้; เปลี่ยนชุดต้องกลับตรวจส่วนที่ได้รับผล | ยังไม่เปิดให้เลือก |
| ออกใช้แล้ว | ให้เลือก ตั้งเป็นรุ่นเริ่มต้น หรือเลิกให้เลือกใหม่ | ใช้ได้ |
| เลิกให้เลือกใหม่ | เก็บให้การอ้างอิงเดิมใช้ต่อ ดูประวัติ และพิจารณาเปิดให้เลือกอีกครั้ง | ใช้ต่อจากเอกสาร/แม่แบบที่อ้างอยู่แล้วได้ |

ทางเดินหลัก: เตรียม → รอตรวจ → พร้อมออกใช้ → ออกใช้แล้ว → เลิกให้เลือกใหม่.
ตรวจไม่ผ่านไปต้องแก้แล้วส่งตรวจใหม่; ถอน/แก้ชุดที่ยังไม่ออกใช้ให้กลับเตรียม.
การเปลี่ยนสถานะไม่เปิดสิทธิ์แก้ชุดที่เคยออกใช้แล้ว.
ผู้ดูแลสร้าง PDF ทดลองระหว่างตรวจได้ โดยไม่เปิดรุ่นนั้นให้ผู้ใช้เลือกทั่วไป.
เจ้าของยืนยันให้สำเนาเอกสารคงการอ้างรุ่นที่เลิกให้เลือกใหม่เพื่อรักษาหน้าตาได้;
การคัดลอกไม่ทำให้รุ่นนั้นกลับมาเปิดเลือกจากคลัง. Service ต้องยืนยันต้นฉบับและสิทธิ์
ก่อนสืบทอดการอ้างอิง ไม่เชื่อคำกล่าวอ้างใน payload ของผู้ใช้.
สิทธิ์สืบทอดจำกัดรุ่น/น้ำหนัก/ปกติหรือเอียงที่ต้นฉบับมีสิทธิ์; เปลี่ยนชื่อ style ได้
แต่ไม่ได้สิทธิ์เลือก face อื่นเพิ่ม. นำเข้า JSON เองไม่ใช่การคัดลอกที่ Service รับรอง.

- หนึ่งตระกูลมีรุ่นเริ่มต้นสำหรับการเลือกใหม่ได้หนึ่งรุ่น และต้องเป็นรุ่นออกใช้แล้ว.
- เลิกให้เลือกรุ่นเริ่มต้นต้องเลือกตัวแทนหรือยกเลิกค่าเริ่มต้นอย่างชัดเจน ระบบไม่เดาแทน.
- เปิดรุ่นที่เลิกให้เลือกแล้วได้อีกเมื่อยืนยันว่าชุดเดิมยังผ่านเงื่อนไข พร้อมบันทึกประวัติ.
- ลบรุ่นเตรียมได้เมื่อไม่มีการอ้างอิงและไม่มีงานตรวจค้าง รุ่นที่เคยออกใช้ให้เก็บไว้.
- ไฟล์ร่วมต้องไม่ถูกลบตามรุ่นใดรุ่นหนึ่ง การลบต้องคำนึงถึงทุกการอ้างอิง.
- เก็บผู้ทำ เวลา และเหตุผลของการส่งตรวจ ออกใช้ ตั้งค่าเริ่มต้น และเลิกให้เลือก.

เลิกให้เลือกใหม่ไม่แปลว่าไฟล์เสีย. หากไฟล์หาย/เสีย/hash ไม่ตรง ต้องหยุด PDF
ที่ใช้ไฟล์นั้นและแจ้งปัญหา แม้เป็นการอ้างอิงเดิม; ไม่แทนไฟล์ให้อัตโนมัติ.

## 10 ปัญหาที่บันทึกค้างได้และปัญหาที่ต้องปฏิเสธ

เกณฑ์คือโครงสร้างข้อมูลยังเก็บและอ่านกลับได้แน่นอนหรือไม่.
การยอมให้ฟอนต์ไม่พร้อมใน draft ไม่ใช่ยอมให้โครงสร้างเสียได้ทุกแบบ.

| กลุ่มปัญหา | ตัวอย่าง | การบันทึกและ PDF |
| --- | --- | --- |
| โครงสร้างผิด | ชนิดผิด ค่านอกช่วงสัญญา รหัสจำเป็นขาด อ้างอิงภายในกำกวม | ปฏิเสธการบันทึก ระบุตำแหน่ง |
| สิทธิ์/ช่องทางไม่ถูกต้อง | ไม่มีสิทธิ์แก้ หรือส่ง path/URL แทนรหัสคลัง | ปฏิเสธการบันทึก |
| ฟอนต์ไม่พร้อม | ยังไม่เลือก รหัสรุ่นรูปแบบถูกต้องแต่ค้นไม่พบ รุ่นยังไม่ออกใช้ หรือไม่มีรูปแบบที่ขอ | บันทึกได้ แต่ต้องแก้ก่อน PDF |
| อักษรใช้ไม่ได้ | ขาดตัวอักษรหรือจัดรูปชุดอักษรที่ต้องใช้ไม่ได้ | บันทึกได้ แต่ต้องแก้ก่อน PDF |
| ไฟล์/บริการไม่พร้อม | ไฟล์หาย hash ผิด หรือบริการตรวจขัดข้อง | โครงสร้างถูกต้องบันทึกได้ แต่ยังรับรองความพร้อม PDF ไม่ได้และต้องหยุดสร้าง |

การอ้างอิงเดิมไปยังรุ่นเลิกให้เลือกใหม่ยังใช้ได้ตามข้อ 9.
สถานะยังไม่เลือกฟอนต์ต้องมีรูปแบบข้อมูลที่สัญญาอนุญาต ไม่ใช้รหัสปลอมหรือค่าว่างแทน.
รหัสชนิดถูกต้องแต่ค้นไม่พบแยกจากรหัสผิดโครงสร้าง; ไม่ตีความเป็นข้อผิดพลาดแบบเดียวกัน.
ปฏิเสธแล้วต้องไม่เขียนบางส่วนหรือขยับ revision; กติกาสิทธิ์และการแก้ revision ยังใช้.

เมื่อบันทึกสำเร็จ ตอบสองผลแยกกัน:

- บันทึกแล้ว: revision ที่เก็บสำเร็จ.
- ความพร้อม PDF: พร้อม / มีปัญหาต้องแก้ / ยังตรวจไม่สำเร็จ.

แต่ละปัญหามีรหัส ตำแหน่ง เหตุผล และวิธีแก้. ปัญหา style รวมเป็นรายการเดียว
พร้อมจุดที่ใช้; อักษรขาดให้มีตัวอย่างข้อความ/ตำแหน่ง ไม่ส่งรายการซ้ำจนอ่านไม่ไหว.
ผู้ใช้แก้ด้วยการเลือกน้ำหนัก/รูปแบบ ฟอนต์ หรือรุ่นที่รองรับ โดยบันทึกในเอกสาร
ไม่แก้รุ่นคลังเดิม. ก่อน PDF ตรวจ revision และข้อมูลจริงอีกครั้ง
ผลจาก draft เก่ารับรองข้อมูลที่เปลี่ยนแล้วไม่ได้.

## 11 รายละเอียดที่ปิดในช่วง 0 และการพิสูจน์ต่อ

ช่วง 0 ในแผนปิด schema/version, field, unselected, issue codes, owner/API/CLI,
snapshot/revision และธุรกรรมสืบทอดแล้ว พร้อมตัวอย่างรับ–ส่งและเกณฑ์ผ่าน/ไม่ผ่าน.
ไม่คัดรายละเอียดสัญญาซ้ำในเอกสารนี้. การพัฒนาต้องพิสูจน์ parser/storage/round-trip,
Sarabun เดิม, ข้อความตัวแทน/PDF ทุก face และ restore ตามช่วง 1–6;
การปิดสัญญาไม่ใช้แทนผลตรวจเหล่านั้น. UI/custom/variable fonts เลื่อนไปตามขอบเขตช่วงแรก.
