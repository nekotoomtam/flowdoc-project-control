## เป้าหมายและฐาน

รอบถัดไปเน้นสร้างเอกสารเป็นเล่มที่มีหน้าปก สารบัญ เนื้อหา หัว–ท้าย และเลขหน้า
ให้ผู้สร้างแม่แบบกำหนดรูปแบบครั้งเดียว ผู้เรียก API ยังส่งข้อมูลและลำดับรายการ
ระบบประกอบเนื้อหาและจัดหน้า PDF โดยไม่ให้ผู้เรียกส่งกราฟ node หรือพิกัด

ฐานคือ Core/Service release0.1.8, tag v0.1.8:
Core `7b5161c`, Service `78c9491` ตามบันทึก release ที่อ้างด้านบน
ข้อความ ตาราง เซลล์รวม ภาพ cell repeats และ Area ชั้นเดียวเป็นของเดิมที่ต้องรักษา
กติกาหน้าใหม่ต้องไม่อาศัยว่าข้อมูลสั้นหรือมีจำนวนหน้าคงที่

## สิ่งที่เจ้าของยืนยันแล้ว

1. รวมงานระบบหน้ากระดาษเป็นเป้าหมายหลักรอบเดียว เพราะหน้าปก หัวท้าย เลขหน้า
   และสารบัญพึ่งพากติกาหน้าเดียวกัน แต่แบ่งออกแบบ/ตรวจรับเป็นพาร์ตได้
2. แยกสามส่วน: รูปแบบหน้า, ส่วนของเล่ม, หน้าที่จัดออกมาจริง
3. ส่วนเนื้อหาทั่วไปมีหลายหน้าได้ ระบบคำนวณจำนวนหน้าจากเนื้อหาจริง
   ส่วนปกเป็นข้อยกเว้นหน้าเดียวตามข้อตกลงเพิ่มเติมด้านล่าง
4. การแบ่งหน้าไม่สร้างหรือเปลี่ยน authored node เพียงเพราะพื้นที่หมด
5. แม่แบบเก่าที่ไม่ได้ประกาศส่วนของเล่มต้องยังใช้พฤติกรรมเดิมได้
   ความสามารถใหม่เป็นทางเลือกของแม่แบบใหม่/แม่แบบที่ผู้สร้างตั้งใจปรับ
6. ผู้เรียก API จัดข้อมูลตาม contract; การกำหนดรูปแบบหน้าเป็นหน้าที่ผู้สร้างแม่แบบ
7. ร่างเอกสารก่อน แล้วจึงแตก roadmap และรายละเอียดลงมือ ไม่เริ่มโค้ดจากร่างนี้เอง

## สามส่วนของโครงสร้าง

### ข้อตกลงเพิ่มเติมระหว่าง R0 — ปกและพื้นที่ node

เจ้าของรับแนวทางเมื่อ2026-10-10 เป็นข้อกำหนดที่จะทำ ไม่ใช่พฤติกรรมของ0.1.8

- ผู้สร้างแม่แบบกำหนดว่ามี cover; ผู้เรียกส่งค่าตัวแปรตามปกติ ไม่ต้องส่งคำสั่ง
  สร้างปกเพิ่มเพื่อให้ปกที่แม่แบบประกาศไว้เกิดขึ้น
- ปกอยู่หน้าแรกจริงเพียงหน้าเดียว ไม่แสดงเลขและไม่ร่วมการนับเลขหน้า
  หน้าหลังปกเริ่มนับ1; จุดหมายใน PDF ยังใช้หน้าจริง ไม่ใช้เลขแสดงแทน
- เนื้อหาปก wrap ภายในพื้นที่ได้ ถ้าเกินหน้าเดียวให้หยุดออกเอกสารและแจ้งจุดที่
  วางไม่พอ อ้าง node/ตัวแปรต้นทางเมื่อระบุได้ ไม่ต่อปกหน้าใหม่ ไม่ตัดข้อความ
  ไม่ปล่อยให้ล้นจนมองไม่เห็น และไม่ย่อฟอนต์อัตโนมัติ
- ตรวจแม่แบบด้วยข้อมูลตัวอย่าง และตรวจข้อมูลจริงตอนออกเอกสารด้วย
  ตัวอย่างผ่านไม่ได้รับประกันว่าค่าตัวแปรทุกความยาวจะวางได้

เพิ่มความสามารถจองพื้นที่ node โดยแยกความสูงกล่องที่ผู้สร้างกำหนดออกจาก
ความสูงเนื้อหาที่วัดได้ ตัวอย่าง: กล่องชื่อโครงการสูง30mm แม้เนื้อหาสูง10หรือ25mm
กล่องยังใช้30mm; node ถัดไปเริ่มหลังกล่องเดิม เนื้อหาเพิ่มบรรทัดไม่ดันลง
พื้นที่ว่างที่เหลือเป็นส่วนหนึ่งของกล่อง ไม่ใช่การเติม newline

| โหมด | พฤติกรรมที่รับไว้ |
| --- | --- |
| สูงตามเนื้อหา | คงทางเดิมสำหรับเนื้อหาทั่วไป กล่องโตตามข้อความและเลื่อน node ถัดไป |
| ล็อกความสูง | ผู้สร้างกำหนดพื้นที่คงที่ wrap ภายใน; เกินพื้นที่ให้หยุดพร้อม diagnostic ไม่ดัน/ทับ node ล่าง |

การจัดเนื้อหาแนวตั้งภายในกล่องชิดบน/กลาง/ล่างเป็นรายละเอียดออกแบบใน R0
ยังไม่ล็อกชื่อ props หรือค่า default ของ alignment/padding
โหมดจองขั้นต่ำที่เกินแล้วขยายเคยใช้เทียบอธิบาย แต่ยังไม่เพิ่มเป็นโหมดที่ต้องทำรอบนี้
เริ่มออกแบบจาก TextBlock บนปก ไม่อนุมานว่า node ทุกชนิด/เซลล์ตาราง/Area
รองรับล็อกความสูงทันที; R0 ต้องกำหนดชนิดและบริเวณที่รองรับก่อนลงโค้ด
ขนาดกล่องกับ padding ต้องมีนิยามเดียวกันในการวัดและวาด ไม่เพิ่มพิกัดอิสระทั้งหน้า

### ข้อตกลงเพิ่มเติม — เนื้อหาจากแม่แบบกับรายการจาก API

เจ้าของรับแนวทางนี้ระหว่าง R0 เมื่อ2026-10-10:

| ลักษณะเนื้อหา | ผู้กำหนดและวิธีเกิด |
| --- | --- |
| แม่แบบกำหนดไว้ | ผู้สร้างประกาศ เช่น ปก สารบัญ ข้อความท้ายเล่ม ระบบสร้างตามแม่แบบและเติมตัวแปร ไม่รอรายการ content เพื่อให้ส่วนนั้นเกิด |
| พื้นที่รับรายการ | ผู้สร้างกำหนดพื้นที่และรูปแบบที่รับ ผู้เรียกส่งข้อมูล/ลำดับรายการ เช่น เนื้อหาหลักหรือหลักฐาน |

เล่มพื้นฐานเรียง ปกที่แม่แบบกำหนด → สารบัญที่แม่แบบกำหนด → พื้นที่รับ content
รายการ content เข้าเนื้อหาหลัก ส่วนค่ากลางใน data ใช้เติมบนปกได้ตาม binding ปกติ
ไม่ได้บังคับว่าทุกแม่แบบต้องมีปกหรือสารบัญ และไม่สร้างส่วนที่แม่แบบไม่ได้ประกาศ
โครงคงที่ไม่ได้แปลว่าข้อความทุกคำคงที่: ตัวแปรยังเปลี่ยนตามข้อมูลจริงได้

ตัวอย่าง request เชิงแนวคิดสำหรับพื้นที่รับรายการเดียว ไม่ใช่แม่แบบที่ลงทะเบียนแล้ว:

```json
{
  "docKey": "uat-report",
  "version": 1,
  "data": {"projectName": "โครงการตัวอย่าง"},
  "content": [
    {"format": "section-note", "data": {"text": "รายละเอียดการทดสอบ"}}
  ]
}
```

ผู้สร้างแม่แบบต้องประกาศ projectName และ section-note พร้อม schema ที่ตรงกัน
รวมจุดวางปก/สารบัญ/เนื้อหา ปกอ่าน projectName โดยไม่ต้องมี format cover ใน request
ชื่อ field ของโครงแม่แบบใหม่ วิธีอ้าง fragment ของส่วนคงที่ และกติกา content ว่าง
ยังต้องล็อกใน R0 ไม่อนุมานว่าเล่มที่มีปกอย่างเดียวผ่าน validator ปัจจุบันแล้ว
กรณีพื้นที่รับรายการหลายแห่งยังเปิด: ต้องแยกหน้าที่จาก Area ที่มีอยู่ให้ชัด
ไม่ถือว่าตัวอย่าง sections ในแชตก่อนหน้าได้รับอนุมัติเป็น API ใหม่

### ข้อตกลงเพิ่มเติม — ตัวตน ลำดับ และขอบเขตส่วนของเล่ม

เจ้าของรับข้อสรุปห้าข้อเมื่อ2026-10-10:

1. รูปแบบหน้ามี ID ของตัวเอง เก็บขนาด/ขอบ/พื้นที่หัวท้าย หลายส่วนอ้างรูปแบบหน้า
   เดียวกันได้ ชื่อที่แสดงเปลี่ยนได้โดยไม่เปลี่ยนความสัมพันธ์ที่อ้าง ID
2. ส่วนของเล่มมี ID และลำดับแยกกัน ผู้สร้างกำหนดลำดับ ไม่อาศัยลำดับ key ของ
   JSON request ส่วนทั่วไปมีหลายหน้าได้ ยกเว้นปกหน้าเดียวตามกติกาที่รับไว้
3. แต่ละส่วนมีแหล่งเนื้อหาชัด: ปกใช้โครงแม่แบบเติมตัวแปร สารบัญใช้จุดวางที่
   แม่แบบประกาศ เนื้อหาหลักรับ content; ภาคผนวกอาจเป็นโครงที่กำหนดหรือพื้นที่
   รับรายการตามแม่แบบ ไม่บังคับทุกเล่มให้มีส่วนเหล่านี้ครบ
4. หลายพื้นที่รับรายการมี key ที่ผู้สร้างตั้ง เช่น main/appendix ให้ผู้เรียกส่ง
   ข้อมูลถูกพื้นที่ ความสัมพันธ์ภายในอ้าง ID; key กับชื่อที่แสดงไม่ใช่ตัวเดียวกัน
   การเปลี่ยน key อาจกระทบผู้เรียกและต้องอยู่ใน contract/version ที่เผยแพร่
5. รอบแรกเปลี่ยนส่วนของเล่มให้เริ่มหน้าใหม่ ไม่รองรับต่อสองส่วนบนหน้าเดียว
   เปลี่ยน node หรือ format ภายในส่วนเดิมไม่ใช่คำสั่งขึ้นหน้าใหม่

ส่วนของเล่มคุมรูปแบบหน้า การขึ้นหน้า และเลขหน้า ส่วน Area คุมรายการโครงย่อย
ในจุดวางหนึ่ง จึงไม่ใช่สิ่งเดียวกันและไม่สร้างระบบรายการซ้ำขึ้นเอง
R0 ยังต้องตรวจการใช้ Area เดิมกับหลายพื้นที่รับข้อมูลก่อนล็อก JSON request
ข้อสรุปนี้ยังไม่เลือกรูปแบบ sections ใน request, ชื่อ field หรือชนิด ID ใหม่
กติกาส่วนว่างและกรณีส่วนก่อนหน้าจบพอดีหน้าต้องกำหนดเพื่อไม่ให้เกิดหน้าเปล่าเกิน
โดยยังรักษาหลักว่าส่วนที่มีเนื้อหาใหม่เริ่มบนหน้าใหม่

### ตารางความรับผิดชอบของสามส่วน

คำภาษาอังกฤษในตารางเป็นชื่อแนวคิดชั่วคราว ไม่ใช่ชื่อ field/node/API ที่รับรองแล้ว
จัดเป็น define สำหรับงานออกแบบนี้ตาม [Terminology policy](flowdoc-product-terminology.md)
ไม่ประกาศเป็น product truth หรือเปลี่ยน glossary กลางจากเอกสารร่าง

| ส่วน | ข้อมูล/หน้าที่ | สิ่งที่ไม่ควรเก็บปน |
| --- | --- | --- |
| รูปแบบหน้า (page layout definition) | ขนาดกระดาษ ระยะขอบ พื้นที่หัว–ท้าย ใช้ซ้ำได้ | จำนวนหน้าที่วัดได้ พิกัดข้อความจริง |
| ส่วนของเล่ม (document section) | ช่วงเนื้อหา อ้างรูปแบบหน้า กติกาเริ่มหน้าและเลขหน้า | การคัดลอก node เพื่อให้ครบจำนวนหน้าที่คาดไว้ |
| หน้าที่จัดออกมาจริง (laid-out page) | หน้า พื้นที่วางจริง ส่วนต่อเนื่องและการอ้างกลับต้นทาง | การเขียนค่าที่วัดได้ทับแม่แบบ |

ตัวอย่างเชิงความหมาย: ปก → สารบัญ → เนื้อหาหลัก
ปกและสารบัญมีส่วนของตัวเอง เนื้อหาหลักใช้รูปแบบหน้าของเนื้อหา
หากข้อมูลยาวจาก10เป็น30หน้า ส่วนเนื้อหายังคงเป็นส่วนเดิมและได้หน้าจริงเพิ่ม
ตัวอย่างนี้ไม่บังคับให้ทุกเล่มต้องมีสามส่วนหรือชื่อดังกล่าว

## ขอบเขตหกพาร์ตที่จะนำไปกาง roadmap

| พาร์ต | ผลที่ต้องออกแบบให้ชัด | จุดตรวจรับที่เสนอ |
| --- | --- | --- |
| 1. โครงหน้าและส่วนของเล่ม | identity, การอ้างรูปแบบหน้า, ลำดับส่วน, การผูกเนื้อหาและ default | ข้อมูลน้อย/มากยังอยู่ในส่วนที่ถูกต้อง และแม่แบบเก่ายังทำงานตามเดิม |
| 2. ปกและการขึ้นหน้า | หน้าปก หน้าเฉพาะ คำสั่งเริ่มหน้าใหม่และหน้าเปล่าที่ตั้งใจแทรก | ไม่เพิ่มหน้าเปล่าโดยไม่ตั้งใจ และไม่ทำเนื้อหาหาย/ซ้ำ |
| 3. หัว–ท้าย | เนื้อหาที่อนุญาต พื้นที่ซ้ำ การเลือกใช้/ยกเว้น และกรณีวางไม่ลง | เนื้อหาหลักไม่ทับหัวท้าย รวมหน้าแบ่งต่อของตาราง/ภาพ |
| 4. เลขหน้า | หน้าจริงกับเลขแสดง การนับ การซ่อน การเริ่มใหม่และต่อเนื่อง | เลขที่แสดงเป็นไปตามกติกาแต่ละส่วน ไม่ทำจุดหมายในไฟล์คลาด |
| 5. สารบัญ | เลขหน้าที่ใช้แสดง จุดหมายจริง และการรวม/ยกเว้นหัวข้อ | ชื่อและเลขหน้ากดไปหัวข้อถูก แม้มีปกหรือเริ่มเลขใหม่ |
| 6. ตรวจทั้งเล่มและส่งมอบ | fixture รวม compatibility package/API และคู่มือ | PDF ตัวอย่างได้รับการตรวจ และหลักฐานตรงกับชุดที่จะ release |

ตารางนี้เป็นลำดับหัวข้อ ไม่ใช่แผน commit หรือการรับรองว่าพาร์ตละหนึ่งเวอร์ชัน
พาร์ต4–5 พึ่งผลจัดหน้าของพาร์ตก่อนหน้า; กติกาที่ส่งผลย้อนกลับต้องตกลงก่อนลงโค้ด
ไม่ทำทุกความสามารถของโปรแกรมประมวลผลคำเพื่อให้พาร์ตแรกเสร็จ

## การไหลของข้อมูลและขอบเขตเจ้าของที่เสนอ

ผู้สร้างแม่แบบกำหนดโครง → ตรวจแม่แบบและ publish → ผู้เรียกส่งข้อมูล →
เลือก snapshot ที่ล็อก → bind/ประกอบเนื้อหาในส่วนของเล่ม → เตรียมทรัพยากร →
จัดหน้าและเก็บข้อมูลหน้าจริง/จุดหมาย → ลงเลขอ้างอิงและวาด PDF → รายงานผล/ส่งไฟล์
ลำดับภายในระหว่าง resource preparation กับ layout ต้องตรวจโค้ดก่อนล็อกละเอียด
ไม่เพิ่มการจำลอง PDF ทั้งเล่มอีกรอบเพื่อคาดจำนวนหน้า/ETA เป็นข้อบังคับ

- Core: นิยามและ validation ของโครง, binding/composition, layout และ PDF
- Service: เก็บ/publish/snapshot, เปิด contract และรับ request, เตรียมทรัพยากรและ job
- Project Control: ข้อตกลง ขอบเขต roadmap และหลักฐานการรับงานร่วมกัน

Service ไม่ควรมีชุดคำนวณ layout อีกชุดที่ขัดกับ Core
ถ้า contract หรือข้อมูลที่เก็บต้องเปลี่ยน ต้องประเมิน migration/consumer ก่อนลงมือ
ไม่ตัดสินตอนนี้ว่าต้องเพิ่มตารางหรือ node ชนิดใดโดยยังไม่ตรวจความจำเป็น

## กติกาสำคัญที่ต้องตัดสินในการออกแบบพาร์ต

| เรื่องที่ยังเปิด | ต้องได้คำตอบก่อน |
| --- | --- |
| เนื้อหาเดิมและรายการ API จะอยู่ในส่วนไหน; ผู้สร้างกำหนดหรือมีข้อมูลเลือกส่วนอย่างไร | ล็อก contract พาร์ต1 โดยไม่ผลักภาระกราฟ node ให้ผู้เรียก |
| รูปแบบหน้ากำหนดระดับเล่มหรือส่วน และสืบทอด/override ค่าใดได้ | implementation พาร์ต1 |
| การเริ่มส่วนใหม่เมื่อส่วนก่อนหน้าจบพอดีหน้า และพฤติกรรมส่วนว่าง | พาร์ต1–2; รับหลักขึ้นหน้าใหม่แล้ว ไม่รองรับสองส่วนบนหน้าเดียว |
| “เว้นหน้า” คือแทรกหน้าเปล่า ซ่อนเลข ไม่ร่วมการนับ หรือไม่ร่วมสารบัญ | พาร์ต2/4/5 ห้ามใช้คำเดียวแล้วถือว่าความหมายเหมือนกัน |
| การแทน cover ในโครงแม่แบบและ binding ของตัวแปร | พาร์ต2; ข้อจำกัดหน้าเดียวและ overflow error รับแล้ว |
| fixed-height รองรับ node/บริเวณใด, หน่วย, padding, alignment และกรณีกล่องใหญ่เกินหน้า | R0 ก่อนลงมือพาร์ต2; ไม่ขยายเป็นระบบพิกัดอิสระ |
| หัวท้ายรับ TextBlock/ภาพ/ตัวแปรใดได้ สูงตายตัวหรือวัดตามเนื้อหา | พาร์ต3 รวมวิธีรายงานกรณีพื้นที่ไม่พอ |
| รูปแบบตัวเลข การนับหน้าเปล่า การเริ่มนับใหม่ และ total pages | พาร์ต4; ไม่ถือว่าเลขโรมัน/หน้าคู่คี่อยู่ใน scope โดยอัตโนมัติ |
| สารบัญแสดงเลขใดเมื่อซ่อนเลขหน้าหรือส่วนต่าง ๆ มีเลขซ้ำกัน | พาร์ต5 โดยลิงก์ยังอ้างจุดหมายจริง |
| model gate/default/migration และวิธีคงผลของแม่แบบเก่า | ก่อนเปลี่ยนสัญญาและก่อน release |

ข้อเสนอด้าน error: แม่แบบอ้างรูปแบบหน้าที่ไม่มีให้ตรวจตอน validate/publish;
พื้นที่จัดวางไม่พอให้มี diagnostic ที่อ้างกลับส่วน/เนื้อหาต้นทาง ไม่ตัดเนื้อหาเงียบ ๆ
รายละเอียด error code และนโยบายหยุด/ข้ามต้องล็อกเมื่อออกแบบแต่ละพาร์ต

## ชุดตัวอย่างและหลักฐานรับงานที่เสนอ

ใช้แม่แบบเล่มเดียวเป็นตัวอย่างร่วม: ปก → สารบัญ → เนื้อหาที่มี TextBlock,
ตารางเซลล์รวม ภาพ และ Area → ส่วนปิดท้ายที่เลือกกติกาต่างได้
แปรข้อมูลเป็นชุดสั้นและชุดหลายหน้า ไม่สร้างแม่แบบเฉพาะที่หลบกรณีต่อหน้า

ตรวจอย่างน้อย: ลำดับไม่หาย/ซ้ำ, ขอบเขตพื้นที่ไม่ทับกัน, การต่อหน้าอยู่ในส่วนเดิม,
เลขหน้าตรงกติกา, ลิงก์สารบัญถูก, snapshot เก่าไม่เปลี่ยนจากการแก้ current,
และตัวอย่างเก่ายังผ่านสัญญาเดิม แยกการตรวจอัตโนมัติกับการดู PDF จริงของเจ้าของ
ขนาดชุดทดสอบและ golden comparisons ให้ roadmap ระบุเมื่อกติกาชัด
การทดสอบขีดจำกัด/โหลดหนักเป็นงานแยก ไม่ใช้แทนการตรวจความถูกต้องของทั้งเล่ม

## สิ่งที่เลื่อนออกจากรอบนี้

ยังไม่ทำ DOCX, frontend/editor, undo/redo, Columns หรือตารางซ้อนใน cell,
Area ซ้อนหรือโครงย่อยกลางแชร์กัน, redesign DB ทั้งระบบ, คิวหลาย worker,
SLA/เปอร์เซ็นต์รวม/ETA หรือ performance overhaul
ตรวจผลกระทบที่จำเป็นต่อหน้ากระดาษได้ แต่ข้อค้นพบที่ขยาย scope ต้องเสนอแยก
การทำหน้าไม่ได้รับรองว่าเว็บ/PDF/DOCX จะเหมือนกันเองในอนาคต

## วิธีเดินต่อและการออกรุ่น

เจ้าของให้กาง roadmap เมื่อ2026-10-10 แล้ว ดู
[Roadmap R0–R6](flowdoc-page-system-roadmap-2026-10-10.md)
ร่างนี้ยังเป็นฐานข้อกำหนด ส่วน roadmap เป็นลำดับผลส่งมอบและการตรวจรับ
ปัจจุบันเริ่ม R0 แบบ read-only และตกลงกติกาบางส่วนแล้ว ยังไม่มี implementation

ขั้นถัดไปเดินตาม roadmap และคลี่คำถามใน R0 ให้ได้สัญญาที่ใช้ลงมือ R1
พร้อม acceptance และ proof ของพาร์ตที่กำลังจะทำ

คำถามเปลี่ยน architecture/contract โดยไม่ resolve ก่อน

เลือกเลข release เป้าหมายเมื่อ scope/compatibility ชัด ไม่สมมติเป็น0.2.0จากชื่อรอบ
release รอเกณฑ์ที่ล็อกใน roadmap ครบและการอนุมัติที่ครอบคลุม
